# Onyx's 2026 feature map splits along a hard EE line

Onyx (formerly Danswer, github.com/onyx-dot-app/onyx) is a genuinely open-core enterprise AI search/chat platform whose Community Edition — **MIT-licensed** and covering chat, RAG, ~50-56 connectors, custom agents, Actions/MCP, and Deep Research — is functionally complete for a single-tenant, low-governance deployment, while a hard, code-enforced Enterprise Edition boundary gates everything related to *governing* that deployment at scale: SAML/OIDC SSO, SCIM provisioning, document-level permission sync, custom RBAC groups, usage analytics/audit, encrypted secrets, whitelabeling, and hook extensions. This is not a soft marketing distinction — the EE code physically lives in `ee/`-suffixed directories that are explicitly carved out of the repository's MIT grant and covered instead by a separate, non-open-source "Onyx Enterprise License" that forbids production use without a paid subscription ([LICENSE](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE)). Two 2026 architecture shifts matter for any technical comparison: Onyx completely removed Vespa as a search backend in v4.0.0 (May 2026), standardizing on OpenSearch alone, and it quietly deleted its reranking/cross-encoder infrastructure as dead code in the same window, meaning today's relevance stack leans on hybrid BM25+vector fusion, contextual chunk enrichment, and LLM-driven chunk selection rather than a dedicated reranker stage. Deep Research, MCP client/server support, and the custom-agent/Actions framework are all Community Edition — Onyx's competitive pitch is that the *AI capability* is free and the *governance layer* is the product it sells. For a KnowFlow gap analysis, the sharpest contrasts to track are: connector permission-sync breadth (Onyx claims 8-11 sources, EE-gated), the MCP dual-role (client and server) support, and the source-available-but-not-open-source nature of everything an enterprise buyer actually needs to trust the system with real access control.

## 1. Enterprise search

Search is hybrid, combining BM25 keyword matching with vector similarity, executed against a single pluggable document-index backend. That backend changed materially in 2026: Onyx historically supported both Vespa (its original, high-performance default) and OpenSearch, with a documented migration path between them, but **v4.0.0 (May 26, 2026) removed Vespa entirely**, making OpenSearch the sole index going forward — any source describing Vespa as current is now stale ([Onyx Changelog](https://docs.onyx.app/changelog); [v4.0.0 notes](https://newreleases.io/project/github/onyx-dot-app/onyx/release/v4.0.0)). The migration was staged: v3.0.0 (March 9, 2026) shipped "the full Vespa to OpenSearch migration toolchain with live progress monitoring" before the outright removal two releases later ([Onyx Changelog](https://docs.onyx.app/changelog)). Retrieval scoping is available through Document Sets — admin-curated bundles used as search filters ([Document Sets docs](https://docs.onyx.app/admins/managing_features/document_sets)) — plus source-type filters, a generic tag/metadata key-value system, and, as of v4.4.0 (July 21, 2026), explicit time-based filtering on document creation/modification dates ([Onyx Changelog](https://docs.onyx.app/changelog)). Citations are generated via a pipeline that issues multiple parallel queries (semantic rephrasing plus keyword variants), fuses hybrid results with weighted Reciprocal Rank Fusion, merges adjacent chunks for continuity, and has the LLM select and expand the most relevant chunks per document before assembling a cited answer, surfaced in a dedicated sources sidebar in the chat UI ([onyx.app/answers](https://onyx.app/answers); [Chat UI docs](https://docs.onyx.app/overview/core_features/chat)) — though the exact BM25/vector weighting formula is not confirmed by any primary source. v4.3.0 (July 6, 2026) added "conversation-aware scoping," where internal search dynamically selects which connected sources to query per request rather than always searching everything ([Onyx Changelog](https://docs.onyx.app/changelog)), and v4.6.0 (Aug 20, 2026) exposed search as a first-class programmatic surface via a public `POST /api/search` endpoint and CLI command, plus an "Incognito Mode" that excludes conversations from durable records and bypasses indexing for uploads ([Onyx Changelog](https://docs.onyx.app/changelog)).

**Tier:** Hybrid search, doc sets, filters, and citation generation are **Community Edition (MIT)**. **Permission-aware retrieval — automatic document-level ACL enforcement mirrored from source systems — is Enterprise Edition-only**: "Different access to documents is only available in the Enterprise Edition of Onyx" ([Access Controls docs](https://docs.onyx.app/security/architecture/access_controls)). CE deployments get keyword/semantic/hybrid search and doc-set curation but no automatic enforcement of source-system permissions, meaning a CE-only deployment can technically over-expose documents unless admins manually manage per-user/group access.

## 2. Connectors: roughly 50-56 sources, sync mechanisms are poll-based, permission sync is EE-gated

The authoritative connector count comes from the `backend/onyx/connectors/` directory in the GitHub repo, which contains roughly 56 connector-specific subdirectories as of September 2026: Airtable, Asana, Axero, Bitbucket, Blob storage (unified S3/GCS/R2/Oracle Cloud Storage), BookStack, Box, Braintrust, Canvas (Instructure LMS), ClickUp, Coda, Confluence, Discord, Discourse, Document360, Dropbox, Drupal Wiki, Egnyte, File (upload), Fireflies, Freshdesk, GitBook, GitHub, GitLab, Gmail, Gong, Google Drive, Google Sites, Guru, Highspot, HubSpot, IMAP (generic email), Jira, Linear, Loopio, LumApps, MediaWiki, Notion, Outline, Outlook, ProductBoard, Salesforce, SharePoint, Slab, Slack, Teams, TestRail, Web (crawler), Wikipedia, XenForo, Zendesk, Zoom, and Zulip ([GitHub directory listing](https://github.com/onyx-dot-app/onyx/tree/main/backend/onyx/connectors)). The marketing site rounds this to "40+" and names a representative subset ([onyx.app/connectors](https://onyx.app/connectors)). Notably absent as *standalone* directories: OneDrive (very likely folded into the SharePoint/Outlook Microsoft Graph scope) and Sitemap (very likely a mode of the Web connector) — neither is confirmed, both are inferred from the absence of dedicated code.

The connector framework itself is architecturally documented (not marketed as a distinct "SDK" product) around four sync patterns defined in `backend/onyx/connectors/README.md`: **Load Connector** (bulk, point-in-time re-index), **Poll Connector** (incremental refresh within a time range — the primary mechanism for "incremental sync"), **Slim Connector** (lightweight ID-only fetch used for pruning stale entries and permission-sync consistency checks), and **Event-Based Connectors**, which the README explicitly labels "currently designed for future implementation" — meaning **no connector in the current lineup uses real-time webhook push sync as of September 2026; all sync is scheduled/polling-based** ([connectors/README.md](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)). Default connector behavior is a 30-minute refresh interval and a 30-day pruning cycle, both admin-configurable ([Connectors Overview](https://docs.onyx.app/admins/connectors/overview)). A per-connector breakdown of exactly which ones are Load-only (full re-index every cycle, no incremental) versus Poll/Checkpointed (true incremental) was not verified for each of the ~56 connectors individually — this is a real gap requiring source-file-level inspection.

Permission sync — automatic document-level ACL mirroring from the source system — is confirmed for a specific, EE-gated subset. The marketing connectors page names eight: **Confluence, Jira, GitHub, Google Drive, Gmail, Slack, Salesforce, and SharePoint** ([onyx.app/connectors](https://onyx.app/connectors)). A separate docs-overview summary lists a broader set adding **Box, Canvas, and Outlook**, for a union of eleven ([Connectors Overview](https://docs.onyx.app/admins/connectors/overview)). The GitHub connector's permission sync has a specific operational quirk: it requires users to maintain a *publicly visible* email address on their GitHub profile, or the system cannot map GitHub permissions to Onyx users ([GitHub Connector docs](https://docs.onyx.app/admins/connectors/official/github)). Architecturally, permission sync is implemented via a `CheckpointedConnectorWithPermSync` interface class distinct from plain Load/Poll connectors, and the actual per-source sync logic is delegated at runtime to an EE-only module (`onyx.external_permissions.sync_params`), confirming the EE gate is a genuine module boundary, not a UI-only restriction ([access.py](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/access/access.py)). Every connector, regardless of type, has three access-type configurations: **Private** (creator plus explicitly assigned users/groups), **Public** (all Onyx users), and **Auto Sync Permissions** (EE-only ACL mirroring) ([Connectors Overview](https://docs.onyx.app/admins/connectors/overview)).

Connector catalog growth is active and ongoing: September 2026 documentation PRs added dedicated pages for Coda, TestRail, and Braintrust, and retroactively published navigation for six connectors that existed in code but were missing documentation (Axero, IMAP, Loopio, MediaWiki, Outline, Wikipedia) ([PR #463](https://github.com/onyx-dot-app/documentation/pull/463); [PR #465](https://github.com/onyx-dot-app/documentation/pull/465); [PR #466](https://github.com/onyx-dot-app/documentation/pull/466); [PR #468](https://github.com/onyx-dot-app/documentation/pull/468)). No explicit connector deprecation or removal announcement was found in this research pass, though one PR title ("chore(connectors): remove unused connector and permission sync code," [PR #14785](https://github.com/onyx-dot-app/onyx/pull/14785)) suggests some cleanup occurred without a clearly identified target.

**Tier:** The connector framework and running most connectors for basic ingestion is **Community Edition (MIT)** — no evidence exists of an entire connector being blocked from CE. **Permission-sync/auto-ACL behavior on any connector is Enterprise Edition-only**, confirmed explicitly per-connector on at least the GitHub connector page ("Permission sync is available only on Cloud and the Enterprise Edition of Onyx," [GitHub Connector docs](https://docs.onyx.app/admins/connectors/official/github)) and generally at the framework level ([Connectors Overview](https://docs.onyx.app/admins/connectors/overview)).

## 3. Chat: full-featured multi-turn UI, persona/agent/assistant are one concept

Onyx's chat interface supports message editing and regeneration, per-session model selection, and — as of v4.5.0 (Aug 4, 2026) — per-session reasoning-effort and temperature controls with model-specific support detection ([Onyx Changelog](https://docs.onyx.app/changelog)). Citations render inline in bracket-numbered footnote style (`[[n]](url)`) cross-referenced to a dedicated sources sidebar populated from internal search and/or web search ([Chat UI docs](https://docs.onyx.app/overview/core_features/chat)). A "Copy with references" feature copies the answer plus a deduplicated, citation-ordered Markdown source list ([PR #14917](https://github.com/onyx-dot-app/onyx/pull/14917)). Feedback is a simple thumbs-up/thumbs-down control visible to admins on hover ([Chat UI docs](https://docs.onyx.app/overview/core_features/chat)), and chats are shareable via a link-based share button. v4.6.0 (Aug 20, 2026) added multi-model comparison rendering in shared chats and an "Incognito Mode" with configurable retention that keeps conversations out of durable records; the same release made chat and Deep Research runs execute to completion server-side regardless of client disconnect, with the stream recording itself as it progresses ([Onyx Changelog](https://docs.onyx.app/changelog)). v4.7.0 (Sept 4, 2026) added swipeable multi-model carousels for narrow screens and pinned response headers ([Onyx Changelog](https://docs.onyx.app/changelog)).

Onyx's docs are explicit that "Personas," "Assistants," and "Agents" are the same concept used interchangeably ([Core Concepts docs](https://docs.onyx.app/developers/core_concepts)). Four built-in agents ship out of the box: Search Agent (id 0, searches the knowledge base), General Agent (id -1, plain chat, no tools), Paraphrase Agent (id -2, search plus exact-snippet quoting), and Art Agent (id -3, image generation) ([Core Concepts docs](https://docs.onyx.app/developers/core_concepts)). Custom agents are configurable via the Admin Panel or API with a name/description/icon, system prompt, conversation starters, knowledge scoping via Document Sets (or hierarchical file/folder selection when OpenSearch is the backend), and a default LLM per agent ([Custom Agents docs](https://docs.onyx.app/admins/agents/overview)). Agents can be shared org-wide, to specific users/groups, or marked "Featured" to surface in an internal "Explore Agents" gallery — there is no evidence of a cross-organization public marketplace ([Custom Agents docs](https://docs.onyx.app/admins/agents/overview)). Sharing mechanics were rebuilt in v4.2.0 with per-share permissions and explicit ownership transfer, and v4.4.0 added labeled "featured" agents that can be highlighted without being fully public ([Onyx Changelog](https://docs.onyx.app/changelog)). No official documentation describes a full chat-history export feature (PDF/Markdown/JSON transcript export) beyond the answer-level "Copy with references" — this is a confirmed gap, not a confirmed absence.

**Tier:** All of chat, persona/agent configuration, sharing, and feedback are **Community Edition (MIT)** — the README states CE "covers all of the core features for Chat, RAG, Agents, and Actions" ([README.md](https://github.com/onyx-dot-app/onyx/blob/main/README.md)), and the Enterprise Edition feature list does not name any chat/persona feature as EE-gated ([Enterprise Edition docs](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)).

## 4. Agents/Actions/MCP: dual-role Model Context Protocol support is the standout 2026 addition

"Actions" (called "Tools" in the backend) are the functions an agent can invoke to interact with external systems, definable by admins via OpenAPI-spec import ([Actions Overview](https://docs.onyx.app/actions/overview)). Built-in Actions include Knowledge (internal search over connected sources), Image Generation (DALL-E 3), Internet/Web Search (via Serper, Google PSE, Brave, SearXNG, an in-house crawler, and Firecrawl/Exa support), and, as of v4.0.0, an opt-in Coding Agent with bash and file-download tool access, disabled by default ([Core Concepts docs](https://docs.onyx.app/developers/core_concepts); [Onyx Changelog](https://docs.onyx.app/changelog)).

The most significant capability added in 2026 is genuine **dual-role Model Context Protocol (MCP) support**: "Onyx can be configured to be an MCP client and allow your Agents to retrieve data or perform operations," and separately, "Onyx can also act as an MCP server to connect Claude, Cursor, and other AI tools to your Onyx knowledge base" ([MCP docs](https://docs.onyx.app/admins/actions/mcp)). As an MCP client, admins add servers through an "MCP Actions" dashboard by name, description, and URL; the connection supports **HTTP/Streamable-HTTP transport only — stdio-based local MCP servers are not supported** — with authentication options of No Auth, API Key (shared or per-individual), OAuth (with dynamic client registration support), or Pass-Through OAuth ([MCP docs](https://docs.onyx.app/admins/actions/mcp)). After connecting, admins can select which of a server's exposed tools to make available to agents. This capability has seen rapid iteration through 2026: v4.4.0 added group and public access control for MCP servers plus proactive OAuth token refresh; v4.5.0 let scheduled tasks pre-approve MCP tools so they don't stall on approval prompts; v4.6.0 fixed OAuth discovery for servers that only demand auth at tool-execution time (e.g., BigQuery) and fixed premature token expiration for offline-access grants; v4.7.0 added a dedicated 300-second timeout for MCP tool calls, configurable via `MCP_SERVER_API_REQUEST_TIMEOUT_SECONDS` ([Onyx Changelog](https://docs.onyx.app/changelog)). Third-party community MCP servers also exist that expose Onyx itself as a tool provider to external clients — e.g., ByWaleed/onyx-mcp and lupuletic/onyx-mcp-server — but these are unofficial, community-maintained wrappers, not part of the core repository ([ByWaleed/onyx-mcp](https://github.com/ByWaleed/onyx-mcp); [lupuletic/onyx-mcp-server](https://github.com/lupuletic/onyx-mcp-server)).

**Tier:** Actions, custom agents, and MCP (both client and server roles) are all **Community Edition (MIT)** — the MCP docs carry no licensing caveat, and the Enterprise Edition feature list does not name MCP, Actions, or tool-calling as EE-gated ([Enterprise Edition docs](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)). It is unconfirmed whether a distinct "Code Interpreter" action exists separately from the Coding Agent bash/file toolset.

## 5. Deep Research: free, multi-agent, 2-level hierarchy, unsupported in project chats

Deep Research is a user-toggleable chat mode (activated via an hourglass icon), explicitly not automatic and explicitly unsupported inside "project chats" — a v4.6.0 fix note reads: "The Deep Research toggle no longer appears inside project chats, where selecting it always failed — deep research isn't supported in project chats" ([Onyx Changelog](https://docs.onyx.app/changelog)). Architecturally it is a 2-level multi-agent hierarchy designed specifically to avoid "deep-frying" (information degradation from excessive agent-to-agent handoff layering), per Onyx's own engineering blog: a **Clarification Agent** decides whether clarifying questions would help, a **Planning Agent** produces a high-level plan to cover all angles of the query, an **Orchestrator Agent** runs the primary loop delegating research tasks to sub-agents as tool calls and can redirect them mid-run, **Research Agents** perform lower-level investigations with search-tool access, and **Report Agents** generate intermediate and final reports with numbered inline citations ([Onyx Blog: Building the Best Deep Research](https://www.onyx.app/blog/building-the-best-deep-research)). As of v4.6.0, Deep Research runs — like ordinary chats — execute to completion server-side independent of client disconnection, with the stream self-recording as it progresses ([Onyx Changelog](https://docs.onyx.app/changelog)). Onyx claims a February 2026 leaderboard-topping placement on a "deep research bench," via its own self-submitted benchmark repository — this should be treated as a self-reported marketing claim, not independently adjudicated ([onyx_deep_research_bench](https://github.com/onyx-dot-app/onyx_deep_research_bench)). No source specifies a hard minimum model requirement (e.g., a reasoning-tier model) for Deep Research to function.

**Tier:** Deep Research is explicitly and unambiguously **Community Edition (MIT)** — Onyx's own open-source statement says "Onyx's core capabilities—including RAG, deep research, custom agents, and more—[are] completely free for every organization, regardless of size or budget" ([Open Source Statement](https://docs.onyx.app/overview/miscellaneous/open_source_statement)).

## 6. RAG/search internals: contextual chunking replaces reranking as the 2026 relevance lever

Chunking is token-aware (using a `BaseTokenizer` sized to the embedding model's context window) rather than fixed-character-based, and an optional "Multipass Indexing" mode creates multiple chunk-size variants per document to help hybrid search identify relevant passages ([Search Configs docs](https://docs.onyx.app/admins/advanced_configs/search_configs); [DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)). Chunks are enriched with metadata suffixes and title prefixes before embedding. The most notable 2026-era RAG feature is **Contextual RAG**: an `enable_contextual_rag` setting that has the LLM generate document- and chunk-level summaries during indexing, folding this generated context into the text before it's embedded — functionally similar to Anthropic's published contextual-retrieval technique — and confirmed as actively maintained as recently as v4.6.0, which added forward-only re-indexing support for Contextual RAG model updates ([PR #2793](https://github.com/onyx-dot-app/onyx/pull/2793); [Onyx Changelog](https://docs.onyx.app/changelog)). Embedding models are pluggable: cloud options like Cohere and Google are docs-recommended, with self-hosted alternatives (Nomic, BGE, E5) also supported, though the exact out-of-the-box default was only confirmed via a secondary/marketing source, not primary docs ([Search Configs docs](https://docs.onyx.app/admins/advanced_configs/search_configs)).

The single most consequential and under-reported change is that **reranking infrastructure was removed as dead code in 2026**: PR #14781 deleted the `RerankingModel` class and its cross-encoder provider clients (Cohere, LiteLLM, AWS), along with intent-classification models, justified by static-analysis tooling finding no runtime references — "Nothing in the backend calls a reranker now," though database columns for reranking settings and a frontend `RerankerProvider` type remain as vestiges ([PR #14781](https://github.com/onyx-dot-app/onyx/pull/14781)). This is a genuine architecture departure from the "hybrid search plus cross-encoder rerank" pattern common elsewhere in RAG platforms, and from Danswer-era descriptions of Onyx itself; current relevance ranking instead relies on hybrid BM25+vector fusion (via weighted Reciprocal Rank Fusion), contextual chunk enrichment, and LLM-driven chunk selection at answer-generation time. Query rewriting exists via "Multilingual Expansion" (rephrasing queries into other configured languages for cross-language retrieval) and a described multi-query generation pattern (semantic plus keyword variants) ([Search Configs docs](https://docs.onyx.app/admins/advanced_configs/search_configs); [onyx.app/answers](https://onyx.app/answers)). v4.1.0 (June 2026) added query-embedding caching for repeated queries and upgraded the backend to Python 3.13 ([Onyx Changelog](https://docs.onyx.app/changelog)). No primary source discloses default chunk size or overlap in tokens — a genuine documentation gap.

**Tier:** All RAG/search internals described here — chunking, Contextual RAG, embedding model choice, query expansion — are **Community Edition (MIT)**. Reranking is functionally **removed/dead** as of the 2026 PR, not a tiered feature; whatever UI/DB vestiges remain should be treated as non-functional legacy artifacts, not an active experimental feature.

## 7. Document processing: broad format coverage, structured tabular indexing, no confirmed OCR

The generic File connector accepts `.txt, .pdf, .docx, .pptx, .xlsx, .csv, .md, .mdx, .conf, .log, .json, .tsv, .xml, .yml, .yaml, .eml, .epub` ([File Connector docs](https://docs.onyx.app/admins/connectors/official/file)). 2026 releases added several document-processing capabilities in sequence: v3.3.0 (May 4, 2026) introduced section-based chunking for XLSX/CSV producing field-value and summary chunks, extended by v4.5.0's "Tabular Indexing" for spreadsheets and CSVs as structured content ([Onyx Changelog](https://docs.onyx.app/changelog)); v4.0.0 added embedded image extraction from PDFs during indexing; v4.3.0 hardened large-file handling by streaming spreadsheets row-by-row and isolating PDF extraction in a subprocess; and v4.7.0 (Sept 4, 2026, the most recent confirmed release) removed the local `unstructured` parsing package in favor of retaining only its hosted API client, and switched Playwright to a headless-shell-only configuration, cutting image size by 364 MB ([Onyx Changelog](https://docs.onyx.app/changelog)). This last change is worth flagging for a competitive audit: self-hosted Onyx deployments may now depend on an external hosted parsing service (the Unstructured API) rather than a fully local library for complex-format document extraction.

Image content is handled via vision-model summarization (`summarize_image_with_error_handling`), meaning embedded images are converted to LLM-generated text descriptions rather than passed through classic OCR text-layer extraction — no primary source confirms a true OCR pipeline (e.g., Tesseract-style scanned-text recognition) exists anywhere in Onyx as of this research ([DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)). Chunk identity uses a deterministic-UUID function (`get_uuid_from_chunk`), which is suggestive of a deduplication mechanism but is not documented by that name — treat as an inference, not a confirmed dedup feature. The connector framework's four sync patterns (Load, Poll, Slim, Event-based-future) apply to document ingestion generally, and v4.4.0 added independent per-connector credentials for Google Drive and Gmail, enabling multiple distinct ingestion configurations of the same connector type ([Onyx Changelog](https://docs.onyx.app/changelog)).

**Tier:** All document-processing capabilities described are **Community Edition (MIT)**; none appear on the Enterprise Edition feature list.

## 8. Permissions/groups/users/admin: a role-system migration is landing mid-2026, and custom groups stay EE-only

Onyx's role model is in active transition. The legacy scheme — Admin, Basic, Curator, Global Curator — is being replaced starting in v4.7 by a group-based model with "Group Managers": Curators historically could "manage connectors and documents within the specific groups where they hold Curator status," assigned per-group by Admins, with Global Curators automatically curating every group they belong to ([Curators Overview](https://docs.onyx.app/admins/curators/overview)). Under the new model, "the Curator roles go away, but the capability they provided — scoped, per-group management — is preserved through Group Managers," with existing Curators auto-converting with no lockout, and the `CURATORS_CANNOT_VIEW_OR_EDIT_NON_OWNED_ASSISTANTS` environment variable being removed entirely ([What's Changing in Permissions](https://docs.onyx.app/admins/permissions/whats_changing)). Account types include Standard (assignable to groups), Service Account (API-key-backed, access derived from assigned groups), Slack Bot, External User, and Anonymous ([Users and Groups docs](https://docs.onyx.app/admins/user_management/users_and_groups)). Groups are the load-bearing permission primitive: they gate access to private Connectors, Document Sets, and Agents, and can carry per-group LLM token rate limits; critically, "an account that belongs to no group has no permissions" ([Users and Groups docs](https://docs.onyx.app/admins/user_management/users_and_groups)).

**Custom, admin-configurable user groups beyond the two defaults (Admin and Basic) are explicitly Enterprise Edition-only** — the same source states plainly: "Custom groups and configurable group permissions are an Enterprise Edition feature" ([What's Changing in Permissions](https://docs.onyx.app/admins/permissions/whats_changing)). This is reinforced by the Enterprise Edition doc page, which lists "Fine-grained, group-based access control for Connectors, Document Sets, and Agents. Available in v4.7+" alongside "Permission Sync Connectors," "Encrypted Secrets," and general "fine-grained RBACs" as EE capabilities ([Enterprise Edition docs](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)). Document-level access control itself is likewise EE-only in both its implementation modes — automatic mirroring from external sources and direct manual assignment — per the Access Controls doc: "Different access to documents is only available in the Enterprise Edition of Onyx" ([Access Controls docs](https://docs.onyx.app/security/architecture/access_controls)). It could not be confirmed whether CE admins face any restriction on configuring connectors, personas, LLM providers, or API keys themselves (this is implied but not explicitly enumerated by any single fetched source).

**Tier:** Basic Admin/Basic group scaffolding, Standard/Service Account user types, and general admin-panel connector/persona/LLM configuration are **Community Edition (MIT)**. **Custom user groups, fine-grained group-based RBAC, and document-level permission control (both auto-sync and manual assignment) are Enterprise Edition-only.** The Curator/Global Curator role is **deprecated/being removed** as of v4.7, replaced by Group Managers.

## 9. Analytics/feedback: usage dashboards and audit logging sit in a genuine CE/EE-vs-pricing-tier gray zone

The chat feedback mechanism itself — thumbs-up/thumbs-down on hover, visible to admins — is a Community Edition feature ([Chat UI docs](https://docs.onyx.app/overview/core_features/chat)). Beyond that, the README lists "usage analytics by teams/LLMs/agents" (described as "usage graphs broken down by teams, LLMs, or agents") and "query history/audit logging" (described as auditing "usage to ensure safe adoption of AI in your organization") explicitly under Enterprise Edition ([README.md](https://github.com/onyx-dot-app/onyx/blob/main/README.md)), and the Enterprise Edition docs page independently confirms analytics as "Detailed insights into user queries and system usage" under its EE feature list ([Enterprise Edition docs](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)).

There is a real, documented tension worth flagging rather than resolving by assumption: the pricing page lists "Query History & Usage Dashboards" as included in the **$20/user/month self-serve Business tier**, not reserved for the custom-quote Enterprise tier ([onyx.app/pricing](https://onyx.app/pricing)). The most defensible reconciliation is that Onyx-the-vendor commercially bundles some EE-licensed code (query history, usage dashboards, RBAC, permission inheritance) into its own lower-priced Business cloud tier, even though that same code is legally EE-licensed and would require a full Enterprise License to run in a self-hosted deployment outside Onyx's own cloud contract terms. In other words: **"Enterprise Edition" as a licensing/code concept and "Enterprise" as a pricing-tier name are not the same thing**, and reports conflating the two will misstate what a self-hosting customer actually gets for free. No admin-facing feature was confirmed for filtering specifically to "documents that received negative feedback," and no native usage-based billing/cost-tracking mechanism was found documented for self-hosted admins beyond the analytics dashboards themselves.

**Tier:** Thumbs up/down feedback capture is **Community Edition (MIT)**. Usage analytics (by team/LLM/agent), query history, and audit logging are **Enterprise Edition-licensed code**, though Onyx's own Business cloud tier ($20/user/month) commercially includes some of this EE-licensed functionality — self-hosted CE users do not get it without a license.

## 10. API: broad REST coverage, built-in OpenAPI explorer, no confirmed SDK or public rate limits

Onyx exposes what it calls "nearly every Onyx feature" through a REST API spanning Chat (session creation/messaging), Search (internal and web search endpoints), Document Management (connector and document-set administration), and Agents (creation/management) ([Overview & Auth docs](https://docs.onyx.app/developers/overview)). Two authentication mechanisms exist: **API Keys**, created by admins as distinct service-account users whose access derives from assigned groups (None, Basic, Admin, or custom), and **Personal Access Tokens (PATs)**, user-created with configurable expiration (7 days to never) and granular scopes (Search-Read, Chat-Read/Write, LLM Gateway-Use) — both authenticate via Bearer token in the `Authorization` header ([Overview & Auth docs](https://docs.onyx.app/developers/overview)). Base URLs differ by deployment: `https://cloud.onyx.app/api` for Onyx Cloud, `https://your-self-hosted-onyx.com/api` for self-hosted instances, each exposing a built-in OpenAPI/Swagger explorer at `/api/docs` ([Overview & Auth docs](https://docs.onyx.app/developers/overview)). The API follows SemVer 2.0.0 with major-version breaking changes flagged, returns JSON, and signals authorization failures as HTTP 403 with an `INSUFFICIENT_PERMISSIONS` code. User-role management is itself API-driven, exemplified by a documented "Set User Role" endpoint ([Set User Role docs](https://docs.onyx.app/developers/api_reference/user_management/set_user_role)).

No official Python or JavaScript/TypeScript SDK was found referenced anywhere in the fetched documentation — this should be treated as unconfirmed rather than definitively absent, since a direct PyPI/npm registry search was not performed. Likewise, no explicit rate-limiting policy (requests per minute per plan tier) was surfaced in the developer overview.

**Tier:** The core chat/search/document/connector API is **Community Edition (MIT)**, consistent with the README's framing of Chat/RAG/Agents/Actions as CE core features. The Enterprise Edition docs page separately lists "Enterprise Edition APIs with extended access" as its own EE-gated capability ([Enterprise Edition docs](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)) — implying an additional API surface tied to EE-only admin/permission/SCIM functionality layers on top of the generally-available core API.

## 11. Auth/SSO: Basic auth and Google OAuth are free; SAML/OIDC and SCIM are Enterprise Edition-gated

Email/password (Basic) authentication "is always enabled and works out of the box, with no configuration needed," and the first user to sign up automatically becomes an admin ([Basic Auth docs](https://docs.onyx.app/deployment/authentication/basic)). The `AUTH_TYPE` environment variable selects among `basic`, `google_oauth`, `oidc`, `saml`, or `cloud` ([Basic Auth docs](https://docs.onyx.app/deployment/authentication/basic)). The pricing page places Basic Auth and Google OAuth in the $20/user/month Business tier, while **OIDC/SAML SSO is reserved for the Enterprise tier** ([onyx.app/pricing](https://onyx.app/pricing)) — and this is backed by the same code-level licensing mechanism documented elsewhere: SAML/OIDC implementation code lives under the `ee/`-suffixed directories excluded from the MIT grant and governed by the separate Onyx Enterprise License ([LICENSE](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE)). The precise, defensible framing for a competitive report is therefore: **"SSO" is ambiguous as an umbrella term** — Google OAuth is itself a form of SSO available in the lower/free tier, so the accurate claim is "SAML 2.0 and OIDC SSO specifically are Enterprise Edition-gated," not "all SSO requires Enterprise."

SCIM 2.0 provisioning is documented as a distinct, functioning capability: "automated user and group provisioning with SCIM 2.0, including user provisioning..., user deprovisioning..., group sync, and profile updates to keep user attributes in sync," configured via Admin Panel → Permissions → SCIM, with a generate-once bearer token for the IdP and documented setup guides for Okta and Microsoft Entra ([SCIM docs](https://docs.onyx.app/deployment/authentication/scim)). No single primary source states in so many words "SCIM requires an Enterprise license" — this is a reasonably strong inference from SCIM's grouping alongside confirmed-EE group-sync/RBAC features in the README, but should be presented as inferred rather than directly sourced. Programmatic access via API Keys and Personal Access Tokens (detailed in Section 10) is a first-class, fully documented mechanism regardless of SSO tier.

**Tier:** Basic email/password auth and Google OAuth are **Community Edition (MIT)** / lower pricing tier. **SAML 2.0 and OIDC SSO are Enterprise Edition-only**, both commercially (pricing page) and at the code level (`ee/` directory licensing). **SCIM 2.0 provisioning is very likely Enterprise Edition-gated** (inferred, not explicitly stated in a single primary source). API Key and PAT-based programmatic auth are **Community Edition** and tier-independent.

## 12. Enterprise Edition feature list

Cross-referencing the official Enterprise Edition docs page, the GitHub README's "Onyx for Enterprise" section, and the pricing page yields a consistent core list of EE-gated capabilities: **OIDC/SAML SSO** ("SSO authentication with OpenID Connect and SAML 2.0 providers"); **SCIM-based group syncing and user provisioning**; **Permission Sync Connectors** ("automatically inherit user permissions from external systems," spanning at least Confluence, Jira, GitHub, Google Drive, Gmail, Slack, Salesforce, SharePoint, and per a broader docs list, Box, Canvas, and Outlook); **Group-Based Permissions** (fine-grained, group-based access control for Connectors, Document Sets, and Agents, "available in v4.7+"); **User Groups & RBAC** generally (custom groups beyond the default Admin/Basic); **Usage Analytics** ("detailed insights into user queries and system usage"); **Encrypted Secrets** ("enterprise-grade encryption for all sensitive credentials and API keys"); **Whitelabeling** (custom branding, logos, styling); **Hook Extensions** ("inject custom logic into Onyx's pipeline at defined stages without modifying source code"); **Enterprise Edition APIs** (extended API access); and **Priority Support** (dedicated support with guaranteed response times and white-glove deployment assistance) ([Enterprise Edition docs](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition); [README.md](https://github.com/onyx-dot-app/onyx/blob/main/README.md)). The pricing page adds Enterprise-tier-exclusive deployment/commercial add-ons beyond this core code-level list: On-Premise Deployments, Region-Specific Deployments, Early Access to Features, Custom Integrations, Data Exports, Invoice Billing, Volume Discounts, Higher Education Pricing, and an Enterprise SLA ([onyx.app/pricing](https://onyx.app/pricing)) — several of these (on-prem, region-specific deployment, SLA) are commercial/contractual terms rather than gated code, and should not be conflated with the `ee/`-directory licensing boundary.

Onyx Cloud is stated to include all Enterprise Edition features by default, with a no-limitations free trial offered for evaluation ([Enterprise Edition docs](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)). Pricing itself shows some inconsistency across sources: a directly fetched pricing page shows a two-tier structure (Business at $20/user/month annual, Enterprise at custom/contact-sales pricing), while a third-party aggregator separately claims a $0 "Community," $16/seat "Onyx Cloud," and a $200/seat "Scale" plan — these figures could not be reconciled and the aggregator should be treated as lower-confidence or possibly stale relative to the primary page ([onyx.app/pricing](https://onyx.app/pricing) vs. [SaaSworthy](https://www.saasworthy.com/product/onyx-app/pricing)). The practical three-layer structure that best fits the evidence is: (1) free, self-hosted Community Edition with no EE code entitlement at all; (2) a paid Business self-serve cloud tier that commercially bundles some EE-licensed code (RBAC, permission inheritance, usage/query-history dashboards) without requiring a separate Enterprise License, because Onyx as licensor can offer its own EE code to whichever of its own cloud tiers it chooses; and (3) a custom-quote Enterprise tier unlocking the remainder (SSO/SAML/OIDC, whitelabeling, on-prem, hook extensions, dedicated support, SLA). This means a report claiming "EE = paid license required" is fully accurate only for the top tier — several EE-licensed code paths are already sold at the lower Business price point.

## License section: source-available EE, not open-core-with-conversion

Onyx's licensing is a two-part, single-repository split, not a private-repo model. The repo-root `LICENSE` file states that content under `ee`-named directories — specifically `backend/ee/`, `web/src/app/ee/`, and `web/src/ee/`, each carrying an identical copy of the Enterprise License at its root — is governed by "the Onyx Enterprise License," while "content outside of the above mentioned directories or restrictions above is available under the 'MIT Expat' license," the standard permissive OSI-approved MIT text ([LICENSE](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE)). The Enterprise License itself (copyrighted to DanswerAI, Inc., 2023–present — the corporate name predates the Onyx rebrand and appears unchanged in the license text as fetched) permits modification and patch creation for development/testing without a subscription, but **restricts production use** to holders of "a valid Onyx Enterprise License for the correct number of user seats" who comply with the Onyx Subscription Terms of Service, retains "all right, title and interest" in any modifications for DanswerAI, and "explicitly forbids copying, merging, publishing, distributing, sublicensing, or selling the software" ([backend/ee/LICENSE](https://github.com/onyx-dot-app/onyx/blob/main/backend/ee/LICENSE)).

This makes Onyx's EE tier **source-available, not open-source in the OSI sense** — anyone can read the EE code in the public repository (there is no private/hidden fork), but the license prohibits running it in production, copying it, or redistributing it without a paid Enterprise License covering the correct seat count. Critically, no BUSL-style time-delayed conversion clause was found anywhere in the fetched Enterprise License text: unlike Business Source License schemes that automatically convert to a permissive license after a fixed number of years, Onyx's Enterprise License appears to be a **permanent, non-expiring proprietary restriction** on the `ee/` code with no confirmed sunset date. Purchasing an Enterprise License is therefore best understood as buying a contractual right to run code that is *already visible* in the repository, rather than purchasing access to separate, undisclosed source. A separate GitHub project, `onyx-dot-app/onyx-foss`, exists and is described as "Open Source AI Platform," plausibly a pure-FOSS mirror stripped of `ee/` directories, but its exact relationship to the main repo was not independently verified ([onyx-foss](https://github.com/onyx-dot-app/onyx-foss)). It also remains unconfirmed whether EE features are additionally gated by a runtime license-key/feature-flag check against a license server, or whether enforcement is purely contractual/legal (i.e., nothing technically stops a self-hoster from compiling and running the `ee/` code — the restriction is a license-compliance obligation, not necessarily a technical lock, based on available evidence).

## Conclusion

The single most important structural fact for a KnowFlow gap analysis is that Onyx's open-source grant is unusually generous on *capability* (full RAG, all connectors' basic ingestion, custom agents, MCP client and server roles, and a genuinely sophisticated multi-agent Deep Research pipeline are all MIT) and unusually strict on *governance* (any feature that restricts who can see what — permission sync, custom RBAC groups, SAML/OIDC, SCIM, audit/analytics — sits behind a non-OSI, source-available Enterprise License with no automatic future open-sourcing). That split means KnowFlow's competitive positioning question isn't "does Onyx have feature X" for most AI-facing capabilities, since CE likely already does; it's "does KnowFlow give away governance/permission features that Onyx charges for," which is where genuine differentiation or genuine catch-up work lives. Two areas deserve explicit further verification before this inventory is used for pricing or roadmap decisions: the exact per-connector incremental-sync matrix (Load-only vs. true Poll/Checkpointed) across all ~56 connectors, and reconciling the conflicting pricing figures ($20 vs. $16/seat, and the disputed existence of a $200 "Scale" tier) against a live, human-verified read of onyx.app/pricing.
