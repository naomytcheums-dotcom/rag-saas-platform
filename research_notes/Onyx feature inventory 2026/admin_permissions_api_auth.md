# Onyx (onyx-dot-app/onyx) — Admin/Permissions/Groups/Users, Analytics/Feedback, API, Auth/SSO (2026 state)

## 1. Permissions/Groups/Users/Admin: roles, groups, document-level permission sync, admin panel scope, curator role

### Takeaway
Onyx is in the middle of a role-system migration (landing in v4.7): the legacy Admin/Basic/Curator/Global-Curator role model is being replaced by a group-based model with "Group Managers." Custom user groups with configurable, fine-grained permissions (mapping groups to Connectors/Document Sets/Agents) are an **Enterprise Edition (EE)** feature — Community Edition (CE) only has two fixed groups (Admin, Basic) and no custom group creation. Automatic document-level permission sync from source systems (e.g., Google Drive) is also **EE-only**; CE has no document-level access control at all.

### Cited Findings
- Legacy roles: Curators "can manage connectors and documents within the specific groups where they hold Curator status, and are assigned per-group by Admins. Outside their assigned groups, they have the same access as a Basic user." Global Curators are automatically Curators for every group they belong to. — [Curators Overview](https://docs.onyx.app/admins/curators/overview)
- Upcoming change (v4.7+): "Onyx is moving to group-based permissions, and Curator and Global Curator roles will be removed... The Curator roles go away, but the capability they provided — scoped, per-group management — is preserved through Group Managers." Existing Curators/Global Curators auto-convert to Group Managers with no lockout. — [What's Changing in Permissions](https://docs.onyx.app/admins/permissions/whats_changing)
- The migration also removes the `CURATORS_CANNOT_VIEW_OR_EDIT_NON_OWNED_ASSISTANTS` environment variable; users with Admin role join the Admin group, Basic users join the Basic group, Curators become Group Managers of their prior groups; for new groups, Group Managers must be assigned manually. — [What's Changing in Permissions](https://docs.onyx.app/admins/permissions/whats_changing)
- Explicit CE/EE split for groups: "Custom groups and configurable group permissions are an Enterprise Edition feature." CE users only get the default Basic and Admin groups. — [What's Changing in Permissions](https://docs.onyx.app/admins/permissions/whats_changing)
- Account/user model (current docs): "Standard" accounts are normal users that "can be assigned to groups"; "Service Account" is an API key/service account whose "access [comes] from the groups you pick when creating the key"; Slack Bot, External User, and Anonymous are system-managed account types. — [Users and Groups](https://docs.onyx.app/admins/user_management/users_and_groups)
- Group mechanics: "You can organize users and service accounts into groups to manage access at the same time." Groups let admins "attach private Connectors, Document Sets, and Agents to a Group, granting all users in the Group access to these resources," implement token rate limits for LLM usage, and power the whole permission system. Two default groups exist out of the box: Admin and Basic. Critically, "an account that belongs to no group has no permissions" — [Users and Groups](https://docs.onyx.app/admins/user_management/users_and_groups)
- Document-level permission enforcement/sync: Onyx supports two implementation methods — "Automatically mirroring them from external sources (such as Google Drive, Salesforce, etc.)" or "Directly assigning access to users or groups of users" (the latter described as "less convenient but requires less calls to external APIs"). But: "Different access to documents is only available in the Enterprise Edition of Onyx" — Community Edition has no document-level access control. — [Access Controls](https://docs.onyx.app/security/architecture/access_controls)
- Enterprise Edition doc page enumerates EE-gated permission features explicitly: "Fine-grained, group-based access control for Connectors, Document Sets, and Agents. Available in v4.7+," plus "Permission Sync Connectors for automatic inheritance from external systems," "Encrypted Secrets for credentials and API keys," and "Organize users and maintain fine-grained RBACs." — [Enterprise Edition](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)
- README (GitHub, main branch) confirms the CE/EE split in top-level licensing terms: "Onyx Community Edition (CE) is available freely under the MIT license and covers all of the core features for Chat, RAG, Agents, and Actions. Onyx Enterprise Edition (EE) includes extra features that are primarily useful for larger organizations," explicitly listing "Role Based Access Control: RBAC for sensitive resources like access to agents, actions, etc." as an EE item, alongside SSO, usage analytics, query history/audit logging, custom code execution for PII removal, and whitelabeling. — [README.md](https://github.com/onyx-dot-app/onyx/blob/main/README.md)
- Licensing mechanism backing the CE/EE split: the repo's LICENSE file states "All content that resides under 'ee' directories of this repository is licensed under the Onyx Enterprise License," specifically `backend/ee/`, `web/src/app/ee/`, and `web/src/ee/`; "Content outside of the above mentioned directories or restrictions above is available under the 'MIT Expat' license." — [LICENSE](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE)
- Pricing page confirms tiering: the Business plan ($20/user/month) lists "Basic Auth" and "Google OAuth" plus "RBAC" and permission controls; the Enterprise plan adds "OIDC/SAML SSO," on-prem/region-specific deployment, white-labeling, custom integrations, data exports, invoice billing, volume discounts, dedicated support, and an Enterprise SLA. Both tiers appear to reference "Query History & Usage Dashboards." — [onyx.app/pricing](https://onyx.app/pricing) (via secondary summarization tool — see Gaps)

### Inferences
- Onyx has a genuine, code-enforced CE/EE split (not just a pricing-page distinction): EE-gated code lives in dedicated `ee/` directories carved out of the MIT grant, so document-level permission sync, custom/configurable user groups, and RBAC cannot be legitimately unlocked in self-hosted CE without an Enterprise license key.
- The Curator/Global Curator role concept, which historically was the closest thing to a "scoped admin," is being deprecated in favor of "Group Managers" as of v4.7 — anyone documenting Onyx roles today should describe the *new* model as authoritative and flag Curator as legacy/being removed.
- Admin panel configuration surface (connectors, personas/agents, LLM providers, user/group management, API keys, SCIM) is present in some form in CE, but the *granularity* of what an admin can restrict (custom groups, fine-grained RBAC, document-level sync) is EE-only.

### Gaps
- Could not directly confirm from primary docs whether CE admins can configure connectors, personas, LLM providers, and API keys with no restriction (this is implied by "core features" framing in the README but not explicitly enumerated on a single fetched page).
- Could not fetch a page explicitly listing "domain whitelisting" as an admin panel control; not found in the sources reviewed — treat as a gap, not a confirmed absence.
- The pricing page content was retrieved via an AI-summarization fetch tool rather than a direct read of raw markup, so exact wording/formatting on onyx.app/pricing should be verified independently if precision matters (the underlying facts — Business vs Enterprise feature split — align consistently across multiple independent sources, but I did not see the raw page).

## 2. Analytics/Feedback: usage analytics, query feedback loop, CE vs EE gating, usage-based billing

### Takeaway
Onyx provides admin-facing usage analytics (usage graphs by team/LLM/agent) and query history/audit logging, plus a thumbs-up/thumbs-down feedback mechanism on chat responses — but per the official README, these analytics/audit features are explicitly listed under **Enterprise Edition**, not Community Edition. No evidence was found of a built-in usage-based billing/cost-tracking feature exposed to self-hosted admins beyond the analytics dashboards themselves.

### Cited Findings
- README lists as EE features: "usage analytics by teams/LLMs/agents" and "query history/audit logging," described in-repo as "Usage graphs broken down by teams, LLMs, or agents" and "Audit usage to ensure safe adoption of AI in your organization." — [README.md](https://github.com/onyx-dot-app/onyx/blob/main/README.md)
- Enterprise Edition doc page: analytics is called out as "Detailed insights into user queries and system usage" under the EE feature list. — [Enterprise Edition](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)
- Feedback mechanism: Onyx's Chat UI lets users "give feedback viewable to admins using thumbs-up/thumbs-down buttons when hovering over LLM responses." — [Chat UI](https://docs.onyx.app/overview/core_features/chat) (via search-tool summarization; see Gaps)
- Pricing page reportedly shows "Query History & Usage Dashboards" appearing in both the Business and Enterprise tiers, per a secondary summarization — this conflicts somewhat with the README's framing of analytics/audit logging as strictly EE. — [onyx.app/pricing](https://onyx.app/pricing) vs [README.md](https://github.com/onyx-dot-app/onyx/blob/main/README.md)

### Inferences
- There is a real tension/possible inconsistency between the GitHub README (which puts "usage analytics" and "query history/audit logging" squarely in the EE bucket) and the pricing page (which one summarization pass suggested lists "Query History & Usage Dashboards" as available even on the Business/self-serve tier). This should be flagged to the report writer as a conflict rather than resolved by guessing; the README, as the primary open-source project statement, is likely the more authoritative source for the CE/EE code-level split, while the pricing page reflects Onyx Cloud's commercial packaging (which may differ from self-hosted CE/EE licensing boundaries).
- No dedicated "negative feedback documents review" admin screen was directly confirmed in the pages fetched; the thumbs-down mechanism plausibly feeds into the same analytics/query-history surfaces that are EE-gated, but this is an inference, not a confirmed fact.

### Gaps
- Could not confirm whether admins can specifically filter/view "documents that received negative feedback" as a distinct admin panel feature — no source directly described this capability.
- Could not confirm token/cost usage tracking per LLM provider as a distinct line item (only "usage graphs broken down by... LLMs" was found, which implies but doesn't explicitly state cost/token accounting).
- No evidence found of a native usage-based billing feature for self-hosted deployments (Onyx Cloud itself is usage/seat billed at $20/user/month per the pricing page, but that's Onyx's own SaaS billing, not a feature Onyx ships to its customers for their own end users).
- Did not independently verify whether analytics/query history is fully absent in CE or merely limited in scope (e.g., basic per-user query logs might exist in CE while cross-team/LLM breakdown analytics are EE) — the sources are not granular enough to make this distinction with confidence.

## 3. API: REST API surface, OpenAPI spec, SDKs, rate limiting/plan tiers

### Takeaway
Onyx exposes a broad, self-described "nearly every feature" REST API (chat, search, document/connector management, agents) authenticated via Bearer tokens (API keys for service accounts, or user-scoped Personal Access Tokens), with a built-in OpenAPI/Swagger explorer at `/api/docs` on both Onyx Cloud and self-hosted instances. No official SDKs (Python/JS) were found documented, and no explicit rate-limit policy was found in the fetched developer docs.

### Cited Findings
- "Nearly every Onyx feature is accessible through the Onyx API," covering Chat (session creation and messaging), Search (search and web search endpoints), Document Management (connector and document set management), and Agents (creation and management). — [Overview & Auth](https://docs.onyx.app/developers/overview)
- Two authenticated token types: API Keys ("Created by admins for service accounts. Each key is a distinct service account user in Onyx" with access from assigned groups — None, Basic, Admin, or custom) and Personal Access Tokens ("user-created tokens with configurable expiration (7 days to never) and scopes including Search—Read, Chat—Read/Write, and LLM Gateway—Use"). Both authenticate via Bearer token in the `Authorization` header. — [Overview & Auth](https://docs.onyx.app/developers/overview)
- Base URLs: Cloud is `https://cloud.onyx.app/api`; self-hosted is `https://your-self-hosted-onyx.com/api`. — [Overview & Auth](https://docs.onyx.app/developers/overview)
- OpenAPI explorer is built in and reachable at `https://cloud.onyx.app/api/docs` or `https://your-onyx-domain.com/api/docs` for self-hosted; a curated API Reference exists with interactive/experimentable endpoint pages. — [Overview & Auth](https://docs.onyx.app/developers/overview) / search summary of docs.onyx.app
- API follows SemVer 2.0.0 with major version breaks flagged; responses are JSON; authorization failures return HTTP 403 with an `INSUFFICIENT_PERMISSIONS` error code. — [Overview & Auth](https://docs.onyx.app/developers/overview)
- The Enterprise Edition doc page separately lists "Enterprise Edition APIs with extended access" as an EE-gated capability, implying some API surface area (likely tied to EE-only features like permission sync, RBAC config, or SCIM) is gated behind the Enterprise license even though the general chat/search/document API is broadly available. — [Enterprise Edition](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)
- User role/permission management is itself API-driven: there is a documented "Set User Role" endpoint in the API reference. — [Set User Role](https://docs.onyx.app/developers/api_reference/user_management/set_user_role)

### Inferences
- The core chat/search/document/connector API appears to be part of Community Edition (consistent with the README's framing of Chat/RAG/Agents/Actions as CE "core features"), while an "extended access" layer of Enterprise Edition APIs likely covers EE-only admin/permission/SCIM functionality.
- No rate-limiting details were surfaced in the developer overview page; this may be Cloud-plan-dependent (e.g., a Business vs Enterprise API quota) but nothing concrete was found to confirm or quantify it.

### Gaps
- No official Python or JS/TS SDK was found referenced in any fetched source — this should be treated as "not confirmed to exist" rather than "confirmed absent," since a dedicated SDK repo/package listing was not directly checked (e.g., PyPI or npm search was not performed).
- No explicit rate-limit numbers or policy (e.g., requests/minute per plan tier) were found in the Overview & Auth page or elsewhere in this research pass.
- Did not verify whether the interactive OpenAPI/Swagger UI is public/unauthenticated to browse (view schema) even if calling endpoints requires a token.

## 4. Auth/SSO: methods supported, CE vs EE gating of SAML/OIDC, SCIM, API key auth

### Takeaway
Onyx supports Basic (email/password) auth and Google OAuth as broadly available/CE-tier methods, while enterprise-grade SSO (SAML 2.0 and OIDC) is definitively **Enterprise Edition-gated** — both by the pricing page's tier separation and, more fundamentally, by the code itself living under the MIT-excluded `ee/` directories per the repository LICENSE. SCIM 2.0 provisioning (user/group sync from an IdP) is available and documented, configured via Admin Panel → Permissions → SCIM, and is tied to the same enterprise-tier group/permission features. Programmatic API key auth is supported as a first-class, documented mechanism.

### Cited Findings
- `AUTH_TYPE` env var controls the method: "basic, google_oauth, oidc, saml, or cloud." — [Basic Auth](https://docs.onyx.app/deployment/authentication/basic) (via search-tool summary) 
- "Email/password authentication is always enabled and works out of the box, with no configuration needed. The first user to sign up becomes an admin." — [Basic Auth](https://docs.onyx.app/deployment/authentication/basic)
- "For production deployments, Google OAuth, OIDC, or SAML are recommended, and once SSO works, password login and sign-up can be turned off entirely." — [Basic Auth](https://docs.onyx.app/deployment/authentication/basic) (via search-tool summary)
- README explicitly places SSO under Enterprise Edition: "Single Sign On: SSO via Google OAuth, OIDC, or SAML. Group syncing and user provisioning via SCIM" is listed as an EE capability alongside RBAC and analytics — although note Google OAuth is bundled into that same README bullet even though the pricing page separates plain Google OAuth (Business tier) from OIDC/SAML (Enterprise tier); see Inferences for how to reconcile. — [README.md](https://github.com/onyx-dot-app/onyx/blob/main/README.md)
- Enterprise Edition doc page: "SSO authentication with OpenID Connect and SAML 2.0 providers" and "Customize branding, logos, and styling to match your organization" (whitelabel) are both listed as EE features; also "Permission Sync Connectors for automatic inheritance from external systems." — [Enterprise Edition](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)
- Pricing page: Business tier ($20/user/mo) includes "Basic Auth" and "Google OAuth"; Enterprise tier adds "OIDC/SAML SSO" on top. — [onyx.app/pricing](https://onyx.app/pricing) (via search-tool summary)
- License mechanism: SAML/OIDC code is understood to live under the `ee/` directories that are carved out of the MIT grant and "licensed under the Onyx Enterprise License" per the LICENSE file — meaning self-hosting SAML/OIDC without an Enterprise license/key is not covered by the open-source MIT grant. — [LICENSE](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE); corroborated by secondary analysis: "SAML and OIDC authentication features in Onyx are part of the paid Enterprise Edition and require a license for self-hosted deployments... everything under its ee directories is excluded from that grant and carries separate enterprise terms." — [search-tool synthesis referencing docs.onyx.app/deployment/miscellaneous/enterprise_edition and github.com/onyx-dot-app/onyx/blob/main/LICENSE]
- SCIM 2.0 support: "Onyx supports automated user and group provisioning with SCIM 2.0, including user provisioning..., user deprovisioning..., group sync, and profile updates to keep user attributes in sync." Setup: "Admin Panel → Permissions → SCIM and click Generate SCIM Token" (bearer token for the IdP, shown once); supports Okta and Microsoft Entra provisioning guides; discovery endpoints are unauthenticated; a "Connected" status appears once the IdP makes its first request. — [SCIM](https://docs.onyx.app/deployment/authentication/scim) (via search-tool summary)
- API key auth for programmatic access is a first-class documented method: "API Keys: Created by admins for service accounts. Each key is a distinct service account user in Onyx" with access from assigned groups, and "Personal Access Tokens (PATs)" as user-scoped alternative tokens with configurable expiry and scopes. — [Overview & Auth](https://docs.onyx.app/developers/overview)

### Inferences
- The most defensible, precise statement for the final report: **Basic email/password auth and Google OAuth are available without an Enterprise license (CE/Business tier); enterprise SSO via SAML 2.0 and OIDC is Enterprise Edition-gated**, both commercially (pricing page tier separation) and technically (code under `ee/` directories excluded from the MIT license). This directly answers the "is SSO CE or EE" question with a caveat: "SSO" as an umbrella term is ambiguous because Google OAuth is a form of SSO available in the lower tier, so reports should specifically say "SAML/OIDC SSO is EE-only" rather than "all SSO is EE-only."
- SCIM provisioning, being described alongside group syncing/RBAC in the README's EE feature bullet, is very likely also Enterprise Edition-gated in practice (it depends on the same group/permission model that is confirmed EE-only), though no single source explicitly states "SCIM requires an Enterprise license" in as many words — flagged as an inference, not a directly cited fact.

### Gaps
- No single primary source was found stating in so many words "SCIM requires Enterprise Edition license" — this is inferred from its grouping with other confirmed-EE features (group sync, RBAC) in the README bullet, and should be presented as a reasonably strong inference rather than a directly sourced fact.
- Could not directly fetch docs.onyx.app/deployment/authentication/scim or /oidc or /saml pages with a raw content fetch (only search-engine-summarized snippets were available for some of these); a follow-up direct fetch of these three pages would strengthen citation quality if more tool budget were available.
- Did not verify current MFA/2FA support as part of Basic Auth (out of scope of this assignment's key questions, but noting as an unexplored adjacent area).
