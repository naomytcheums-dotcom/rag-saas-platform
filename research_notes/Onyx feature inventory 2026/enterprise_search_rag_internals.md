# Onyx (onyx-dot-app) — Enterprise Search, RAG/Search Internals, Document Processing (2026 state)

## 1. Enterprise Search: search mechanism, ranking, permission-aware retrieval, filters, citations

### Takeaway
Onyx's search is hybrid (BM25 keyword + vector similarity) run against a pluggable document-index backend that has recently changed: **Vespa was completely removed in v4.0.0 (May 26, 2026), leaving OpenSearch as the sole document index** — a major architecture shift from the historical (Danswer-era and early-Onyx) Vespa-only design. Document-level, permission-aware retrieval (ACL sync from source systems) and admin-assigned "doc sets" both exist, but **automatic permission syncing from external sources (Google Drive, Confluence, Slack, Salesforce, SharePoint, Jira, GitHub, Gmail) is an Enterprise Edition (EE)-gated feature**, not available in the MIT Community Edition.

### Cited Findings
- Onyx's document-index architecture historically supported two backends — Vespa (default, high-performance, complex ranking/large-scale vector search) and OpenSearch (hybrid search, more "standard enterprise search") — chosen via environment configuration, with a documented migration path from Vespa to OpenSearch. — [DeepWiki: Document Search and Indexing Backends](https://deepwiki.com/onyx-dot-app/onyx/8.5-document-search-and-indexing-backends)
- **v4.0.0 (May 26, 2026) release notes: "Remove Vespa as an option entirely" — OpenSearch becomes the sole document index.** Users were warned not to upgrade to v4.0.0 without first running the document-index migration from a v3.x release. — [Onyx Changelog](https://docs.onyx.app/changelog); [v4.0.0 release notes summary](https://newreleases.io/project/github/onyx-dot-app/onyx/release/v4.0.0)
- v3.0.0 (March 9, 2026) shipped the "full Vespa to OpenSearch migration toolchain" with live progress monitoring, confirming the migration was staged over multiple releases before Vespa's outright removal in v4.0.0. — [Onyx Changelog](https://docs.onyx.app/changelog)
- Vespa search (pre-removal) supported hybrid search combining BM25 keyword matching with vector similarity; ranking profiles incorporated a `DOC_TIME_DECAY` factor to prioritize newer documents; indexing was batched for throughput. — [GitHub PR #3552 "More efficient Vespa indexing"](https://github.com/onyx-dot-app/onyx/pull/3552); [DeepWiki 8.5](https://deepwiki.com/onyx-dot-app/onyx/8.5-document-search-and-indexing-backends)
- v4.0.0 also introduced "OpenSearch bulk updates on the indexing hot path with retry-on-transient-failure semantics," indicating OpenSearch is now tuned as the primary write path, not a secondary option. — [newreleases.io v4.0.0 notes](https://newreleases.io/project/github/onyx-dot-app/onyx/release/v4.0.0)
- **Document-level access control is Enterprise-Edition-only**: "Different access to documents is only available in the Enterprise Edition of Onyx." Two mechanisms exist: (1) automatic permission mirroring from external sources (Google Drive, Salesforce, etc.), and (2) direct assignment of access to users/groups. — [Onyx Docs: Access Controls](https://docs.onyx.app/security/architecture/access_controls)
- Onyx's EE feature list explicitly names "Permission Sync Connectors" ("Automatically inherit user permissions from external systems") and "Group-Based Permissions" ("Fine-grained, group-based access control for Connectors, Document Sets, and Agents") as Enterprise Edition capabilities. — [Onyx Docs: Enterprise Edition](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)
- Permission model: access is granted via group membership — Basic (default chat/search), Admin (full system access/config), Custom Groups (EE-only, role-specific), Group Manager (single-group management). — [Onyx Docs: Access Controls](https://docs.onyx.app/security/architecture/access_controls)
- Documents carry an `access_control_list` field used to filter search results at the platform layer so only authorized users see given content ("permission-aware retrieval at the platform layer"). — [Web search synthesis citing docs.onyx.app](https://docs.onyx.app/security/architecture/access_controls)
- "If you set your Connector's access type to Auto Sync Permissions, Onyx will maintain an access control list from the source and restrict users to only see data they have access to. However, permission-syncing connectors are an Enterprise Edition feature." Onyx syncs permissions specifically from Confluence, Jira, GitHub, Google Drive, Gmail, Slack, Salesforce, and SharePoint. — [Onyx Docs: Connectors Overview](https://docs.onyx.app/admins/connectors/overview) (via search synthesis); connector coverage also listed at [onyx.app/connectors](https://onyx.app/connectors)
- **Filters available for search/retrieval**: Document Sets (admin-curated bundles used to scope search), Source Type (restrict to a specific connector, e.g. only Slack), Access Control (ACL-based, automatic), Temporal filters (`last_updated` range queries). A `tag` table stores custom metadata key/value pairs for filtering. — [Onyx Docs: Document Sets](https://docs.onyx.app/admins/managing_features/document_sets); [DeepWiki 8.5 / 7.3](https://deepwiki.com/onyx-dot-app/onyx/8.5-document-search-and-indexing-backends)
- v4.4.0 (July 21, 2026) added "Time-Based Filtering: Documents filterable by creation and modification dates" and independent per-connector credentials for Google Drive/Gmail (multiple connector instances). — [Onyx Changelog](https://docs.onyx.app/changelog)
- Document Sets are described as: "group logically connected documents into a single bundle, which can then be used as a filter when performing searches to control the scope of information Onyx searches over." — [Onyx Docs: Document Sets](https://docs.onyx.app/admins/managing_features/document_sets)
- **Citation generation**: the pipeline generates multiple parallel queries (semantic rephrasing + keyword variants), runs them through the hybrid index, merges results via weighted Reciprocal Rank Fusion, merges adjacent chunks for continuity, has the LLM select/expand the most relevant chunks per document (run in parallel per document), assembles a structured prompt with citations + chat history + keyword matches, and the LLM produces a grounded answer with inline citations linking back to source documents. — [Web search synthesis of onyx.app material](https://onyx.app/answers); [Onyx Docs: Chat UI](https://docs.onyx.app/overview/core_features/chat)
- In the Chat UI, a right sidebar surfaces the sources/citations used to generate the answer, each linking back to the original document for verification. — [Onyx Docs: Chat UI](https://docs.onyx.app/overview/core_features/chat)
- v4.3.0 (July 6, 2026) added "Conversation-Aware Scoping: Internal search dynamically selects connected sources per request," and OCSF-shaped audit logging covering authentication, configuration, and access control. — [Onyx Changelog](https://docs.onyx.app/changelog)
- v4.6.0 (August 20, 2026) exposed search as a first-class product surface: a public `POST /api/search` API endpoint plus a CLI command for programmatic searches, and an "Incognito Mode" where conversations are excluded from durable records and uploads bypass search indexing. — [Onyx Changelog](https://docs.onyx.app/changelog)

### Inferences
- The Vespa→OpenSearch migration (staged v3.0.0 → completed removal v4.0.0, both in 2026) is the single most consequential architecture change to verify against any pre-2026 material: any source (blog posts, older docs, DeepWiki pages not yet refreshed) describing Vespa as Onyx's current search backend is now **stale/incorrect** as of v4.0.0+. Report writers should flag Vespa as "removed / historical" not "default."
- Because permission-sync connectors and document-level ACL are EE-gated, an organization running pure Community Edition (MIT) gets keyword/semantic/hybrid search and doc-set filtering, but NOT automatic enforcement of source-system permissions — meaning CE-only enterprise search could technically expose over-permissioned results unless admins manually manage per-user/group access.
- The "doc sets" mechanism appears to be the CE/EE-agnostic scoping primitive (available broadly), while true ACL-mirroring is the EE differentiator — this distinction is important because doc sets alone do not enforce source-system permissions, they are an admin curation tool.

### Gaps
- Exact ranking/scoring formula (weighting between BM25 and vector score, whether Reciprocal Rank Fusion constants are configurable) is not confirmed from primary docs — only inferred from a search-result synthesis referencing onyx.app material, not a directly quoted primary-source page. Could not independently verify via WebFetch due to tool-call budget.
- Whether OpenSearch's hybrid search in Onyx uses OpenSearch's native "Hybrid Query" / normalization-processor pipeline, or a custom Onyx-side fusion layer, was not directly confirmed from a primary source.
- Full mapping of which specific connectors support permission sync (beyond Confluence, Jira, GitHub, Google Drive, Gmail, Slack, Salesforce, SharePoint) was not exhaustively verified against a current connector-by-connector doc page.

## 2. RAG/Search internals: chunking, embeddings, hybrid search backend, reranking, query rewriting

### Takeaway
Onyx uses token-aware (not fixed-character) chunking with an optional "multipass indexing" mode that creates multiple chunk-size variants per document, plus a newer "Contextual RAG" feature that LLM-generates document/chunk summaries to enrich chunks before embedding. Embedding models are pluggable (cloud APIs like Cohere/Google, or self-hosted open models such as Nomic, BGE, E5). **Reranking infrastructure (cross-encoder clients for Cohere/LiteLLM/AWS, and an intent-classification model) was removed as dead code in 2026** — as of the removal PR, nothing in the backend calls a reranker, though the DB schema and a frontend `RerankerProvider` type remain, leaving reranking's current/future status ambiguous. Query rewriting exists in the form of multilingual query expansion and multi-query generation (semantic + keyword variants) for retrieval.

### Cited Findings
- Chunking is token-based: the `Chunker` class uses a `BaseTokenizer` to "ensure chunks fit within the embedding model's context window," rather than using a fixed character-count chunker. — [DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)
- "Multipass Indexing... creates chunks of varying sizes and stores them in the index. This can help the hybrid search algorithm better identify relevant sources." — [Onyx Docs: Index Settings / Search Configs](https://docs.onyx.app/admins/advanced_configs/search_configs)
- Chunks are enriched with "metadata suffixes and title prefixes to improve semantic search performance" before embedding (`DocAwareChunk` objects). — [DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)
- **Contextual RAG**: an `enable_contextual_rag` flag exists in the `SearchSettings` model; the indexing pipeline (`chunker.py`) generates document- and chunk-level summaries via an LLM using a `DOCUMENT_SUMMARY_PROMPT`, storing them in `doc_summary` / `chunk_context` fields on `DocAwareChunk`, and folds this context into the text that gets embedded — i.e., contextual retrieval similar to Anthropic's "contextual retrieval" technique. — [GitHub PR #2793 "enable and run contextual rag"](https://github.com/onyx-dot-app/onyx/pull/2793); [DeepWiki 7.3](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)
- v4.6.0 (Aug 20, 2026) changelog: "Contextual RAG: Model updates support forward-only indexing without full re-indexing" — confirming Contextual RAG is a current, actively maintained 2026 feature, not deprecated. — [Onyx Changelog](https://docs.onyx.app/changelog)
- Embedding models: docs state "The best embedding models are generally available through a cloud provider such as Cohere or Google," with self-hosted options also available (GPU recommended for indexing throughput). — [Onyx Docs: Index Settings / Search Configs](https://docs.onyx.app/admins/advanced_configs/search_configs)
- A separate synthesis (search-result based, not directly quoted from a primary doc page) states Onyx's default embedding model is **Nomic** (self-hosted), and that local/self-hosted embedding options include **BGE, E5, and Nomic**, or hosted endpoints — giving flexibility between local and API-based models. — [search synthesis referencing onyx.app self-hosted RAG guide](https://onyx.app/insights/self-hosted-rag)
- Reranking is described functionally in docs: "A reranking model will assess and re-organize your search results based on the relevance of the documents to the query," with no specific reranker model named in that admin doc. — [Onyx Docs: Index Settings / Search Configs](https://docs.onyx.app/admins/advanced_configs/search_configs)
- **Reranking backend code removal**: PR #14781 ("chore(search): remove unused reranking and intent model clients") removed the `RerankingModel` class, cross-encoder provider clients (Cohere, LiteLLM, AWS rerank implementations), intent-classification models, and config settings `DEFAULT_CROSS_ENCODER_*` / `INTENT_MODEL_*` / `CONNECTOR_CLASSIFIER_MODEL_*`, justified by a dead-code scan ("Vulture found no static reference to these names... no string reference that the code uses at runtime"). The PR explicitly states "Nothing in the backend calls a reranker now," while noting the search-settings DB columns for reranking remain, and the frontend still has a `RerankerProvider` type but doesn't call these removed Python clients. The author asked a "search owner" to confirm reranking is not coming back in this form — meaning, as documented, **reranking is currently non-functional/dead in the backend even though UI/DB vestiges remain.** — [GitHub PR #14781](https://github.com/onyx-dot-app/onyx/pull/14781)
- Query rewriting: "Multilingual Expansion... rephrases your queries into the specified other languages. This can be helpful for cross-language results." — [Onyx Docs: Index Settings / Search Configs](https://docs.onyx.app/admins/advanced_configs/search_configs)
- v4.1.0 (June 11, 2026): "Query embeddings cached for repeated queries" — a retrieval-performance optimization, and backend upgraded to Python 3.13. — [Onyx Changelog](https://docs.onyx.app/changelog)
- Multi-query retrieval: search-result synthesis describes the pipeline as generating "multiple parallel queries through semantic rephrasing and keyword variants" before hybrid retrieval and Reciprocal Rank Fusion — functioning as a form of query expansion, though this description comes from marketing/blog material (onyx.app/answers) rather than a technical doc page. — [onyx.app/answers](https://onyx.app/answers)
- Search backend: as established in Section 1, the vector+BM25 hybrid search backend is now **OpenSearch exclusively** (post v4.0.0), replacing Vespa. — [Onyx Changelog v4.0.0](https://docs.onyx.app/changelog)
- Indexing pipeline dual-write pattern (per DeepWiki, describing pre/around the Vespa-era architecture): documents split into `TextSection`/`ImageSection`/`TabularSection`, chunked via `Chunker`, embedded via `IndexingEmbedder` calling an `indexing_model_server` (configured by `INDEXING_MODEL_SERVER_HOST`), then persisted to the document index (vector search) and PostgreSQL (relational metadata) — note this DeepWiki description references Vespa as the storage target and **may not yet reflect the v4.0.0 OpenSearch-only architecture**, since DeepWiki content can lag behind the latest release. — [DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)

### Inferences
- The removal of reranker/cross-encoder clients as "dead code" strongly suggests Onyx's current relevance-ranking relies primarily on hybrid (BM25 + vector) fusion plus contextual chunk enrichment and LLM-driven chunk selection at answer-generation time, rather than a dedicated reranking model stage — a meaningful architecture difference from the "hybrid search + cross-encoder rerank" pattern common in other RAG platforms (and different from Danswer-era descriptions that emphasized rerankers).
- The shift from Vespa to OpenSearch likely also explains why reranker code atrophied: OpenSearch's own hybrid-query normalization plus RRF may have made a separate cross-encoder pass redundant or was deprioritized during the migration; this is an inference, not confirmed in any source.
- "Contextual RAG" (chunk/document LLM-generated summaries prepended to chunk text before embedding) is the main 2026-era quality lever Onyx promotes for RAG relevance, functioning as a substitute/complement to semantic chunking and to reranking.

### Gaps
- No primary source gives an explicit numeric default chunk size (tokens) or overlap percentage — docs describe the mechanism (token-aware chunking, multipass variable-size chunking) but not the literal default numbers (e.g., "512 tokens, 50 overlap"). This should be flagged as unconfirmed rather than guessed.
- Could not confirm from a primary source whether reranking has since been reinstated after PR #14781 (the PR itself asked for confirmation it "will not come back in this form," implying uncertainty even to the Onyx team at merge time); no later changelog entry was found confirming or denying a reranker's return in the 2026 releases reviewed (v3.0–v4.7).
- Exact current default embedding model shipped out-of-the-box (vs. configurable options) was not confirmed by a primary docs page — the "Nomic default" claim comes from a secondary/marketing-style source (onyx.app/insights blog), not docs.onyx.app itself.
- Whether OpenSearch's hybrid search in current Onyx uses OpenSearch's built-in neural/hybrid search plugin versus a custom scoring layer was not verified against primary source code or docs due to tool-call budget constraints.

## 3. Document processing: supported formats, indexing pipeline, deduplication, structured data/tables

### Takeaway
Onyx's File connector supports a broad range of formats (PDF, DOCX, PPTX, XLSX, CSV, TXT, MD/MDX, JSON, XML, YAML, EML, EPUB, and more), and 2026 releases specifically added first-class **tabular indexing** (structured field-value chunking for spreadsheets/CSVs) and **embedded image extraction from PDFs**, alongside hardening for large-file processing. The general document-processing library `unstructured` was removed from the pipeline in v4.7.0 in favor of the vendor's hosted API client. Deduplication is implied via deterministic chunk UUIDs but not explicitly documented as a dedup feature; true OCR (as in Tesseract-style text-layer extraction from scanned images) was not confirmed as a current pipeline feature — image handling instead appears to route through vision-model-based image *summarization*, not classic OCR.

### Cited Findings
- Onyx's File Connector supports: `.txt, .pdf, .docx, .pptx, .xlsx, .csv, .md, .mdx, .conf, .log, .json, .tsv, .xml, .yml, .yaml, .eml, .epub`. — [Onyx Docs: File Connector](https://docs.onyx.app/admins/connectors/official/file) (via search synthesis)
- v3.3.0 (May 4, 2026): "Tabular Files: Section-based chunking for XLSX/CSV with field-value and summary chunks" — i.e., structured tabular data gets a dedicated chunking strategy distinct from prose chunking, producing per-field-value chunks plus a summary chunk. — [Onyx Changelog](https://docs.onyx.app/changelog)
- v4.5.0 (Aug 4, 2026): "Tabular Indexing: Spreadsheets and CSVs indexed as structured content with field-value chunks" — reconfirms/extends structured tabular indexing as a maintained, current feature in mid/late-2026 releases. — [Onyx Changelog](https://docs.onyx.app/changelog)
- v4.0.0 (May 26, 2026): "Image Extraction: PDF files now extract embedded images during indexing." — [Onyx Changelog](https://docs.onyx.app/changelog)
- v4.3.0 (July 6, 2026): "Large File Hardening: Spreadsheets streamed row-by-row; PDF extraction isolated in subprocess" — indicating robustness work on the extraction stage for large documents. — [Onyx Changelog](https://docs.onyx.app/changelog)
- v4.7.0 (Sept 4, 2026, the most recent entry found): "Document Parsing: Unstructured package removed; API client retained for document handling," and "PDF Handling: Playwright now uses headless shell only, reducing image size by 364 MB." This confirms Onyx had been using the `unstructured` open-source/API library for parsing and has since dropped the local package dependency (likely keeping only the hosted Unstructured API client), and that Playwright is used somewhere in the pipeline (likely for web/HTML rendering or PDF generation from HTML) as of the newest confirmed release. — [Onyx Changelog](https://docs.onyx.app/changelog)
- Document images/vision content: the indexing pipeline splits parsed content into `TextSection`, `ImageSection`, or `TabularSection` types, and "vision-enabled systems process images via `summarize_image_with_error_handling`" — meaning image content is turned into text via an LLM/vision-model summary rather than classic OCR text-layer extraction (as far as could be confirmed). — [DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)
- Chunk identity uses `get_uuid_from_chunk` to "create a deterministic UUID for each chunk" — a mechanism that could support deduplication (identical chunk content/position maps to the same UUID) though the docs/DeepWiki summary does not explicitly describe a deduplication process by that name. — [DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)
- Connector architecture (contributor README) defines four connector flow types: Load (bulk/point-in-time), Poll (incremental by time range), Slim (lightweight existence/ID-only check for pruning and permission sync consistency), and Event-based (future direction, listens to events). Attachment handling ("Include Attachments") is called out for connectors like Confluence and DrupalWiki. — [GitHub: backend/onyx/connectors/README.md](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)
- v4.5.0 (Aug 4, 2026): "Native Azure Storage: First-class Blob Storage backend for file operations" — an infrastructure/storage-layer addition relevant to where raw ingested files are held. — [Onyx Changelog](https://docs.onyx.app/changelog)
- v4.4.0 (July 21, 2026): "Multiple Connectors: Google Drive and Gmail support independent credentials per connector" — allows multiple distinct ingestion configurations per source type. — [Onyx Changelog](https://docs.onyx.app/changelog)
- End-to-end pipeline (per DeepWiki, caveat below on currency): extraction/parsing → sectioning (text/image/tabular) → chunking (`Chunker`/`DocAwareChunk`, token-aware, metadata-enriched) → embedding (`IndexingEmbedder` via a model server) → storage (index + PostgreSQL metadata). — [DeepWiki: Document Indexing Pipeline](https://deepwiki.com/onyx-dot-app/onyx/7.3-document-indexing-pipeline)

### Inferences
- The combination of v3.3.0 and v4.5.0 changelog entries shows tabular/structured-data support was introduced and then iterated on across 2026, confirming it is a live, currently-supported capability rather than a one-off experiment.
- The removal of the `unstructured` local package in v4.7.0 (keeping only "the API client") suggests Onyx is moving toward relying on the hosted Unstructured.io service (or a similarly externalized parsing service) for complex-format extraction (PDF/DOCX/PPTX) rather than bundling parsing libraries directly — worth flagging as a possible new external dependency/cost for self-hosted deployments.
- No dedicated "OCR" feature (in the classic sense of producing a searchable text layer from a scanned/image-only PDF) was found in any 2026 primary source; the confirmed mechanism for image content is vision-LLM summarization, which is a materially different capability (semantic description vs. verbatim text extraction) and should not be conflated with OCR in the report.

### Gaps
- No source enumerates the *complete* list of connectors and their per-connector supported file types beyond the generic File connector list and the specific formats named in changelogs (PDF, DOCX, PPTX, XLSX, CSV) — a full per-connector matrix (e.g., what Confluence/SharePoint/Slack attachment types are parsed) was not found within the tool-call budget.
- Whether there is an explicit, named "deduplication" feature (e.g., dedup across connectors when the same file is ingested from two sources) is unconfirmed; the deterministic chunk-UUID mechanism is suggestive but not documented as a dedup guarantee.
- Could not verify from a primary source whether true OCR (text-layer recognition for scanned/image-based PDFs) exists anywhere in the pipeline as a fallback to vision-summarization — this should be treated as an open question, not asserted as absent, since only indirect evidence (DeepWiki's vision-summarization description) was available.
- The DeepWiki-sourced pipeline description (extraction → chunk → embed → dual-write to Vespa + Postgres) predates or does not reflect the confirmed v4.0.0 removal of Vespa; readers should treat the *storage* step of that pipeline description as outdated (now OpenSearch, not Vespa) while the extraction/chunking/embedding steps are likely still structurally accurate.
