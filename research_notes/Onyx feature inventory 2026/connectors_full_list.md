## Which connectors are Enterprise Edition (EE) only, or require a paid license?

### Takeaway
Onyx's connector *framework* itself (creating/running most connectors) is Community Edition (CE)/open-source, but the **permission-sync / auto document-level ACL sync capability is gated entirely to Enterprise Edition** — this is a feature-level EE gate that applies across whichever specific connectors implement permission sync, rather than entire connectors being blocked from CE users. No evidence was found of an entire connector (e.g., "Salesforce connector" as a whole) being unusable in CE; rather, CE users can index data via these connectors but cannot get Onyx to auto-restrict document visibility by source-system permissions.

### Cited Findings
- "Permission-syncing connectors are an Enterprise Edition feature." — [Overview - Onyx Documentation](https://docs.onyx.app/admins/connectors/overview)
- GitHub connector doc page states: "Permission sync is available only on Cloud and the Enterprise Edition of Onyx." — [GitHub Connector - Onyx Documentation](https://docs.onyx.app/admins/connectors/official/github)
- The Enterprise Edition docs page lists EE-gated capabilities including: Permission Sync Connectors ("Automatically inherit user permissions from external systems"), Group-Based Permissions (fine-grained access control for Connectors/Document Sets/Agents, "v4.7+"), OIDC/SAML SSO, Encrypted Secrets, User Groups & RBAC, Usage Analytics, Whitelabeling, Hook Extensions, Enterprise Edition APIs, and Priority Support — [Enterprise Edition - Onyx Documentation](https://docs.onyx.app/deployment/miscellaneous/enterprise_edition)
- Onyx offers a free, "fully functional" Community Edition; a Business plan around $20/user/month (annual) or $25/user/month (monthly); and an Enterprise tier with contract-based pricing keyed to user count and number of Onyx instances — [Onyx Pricing](https://onyx.app/pricing) (via search-tool summary, not directly fetched)
- Onyx Enterprise Edition is also distributed via AWS Marketplace — [AWS Marketplace: Onyx Enterprise Edition](https://aws.amazon.com/marketplace/pp/prodview-yz6q33iyvgf5e) (title only, not fetched in depth)

### Inferences
- There does not appear to be any connector that is entirely inaccessible in CE (i.e., "you cannot even connect Salesforce without EE"). The EE gate is specifically on the *permission sync / auto-ACL* behavior, plus adjacent enterprise features (SSO, RBAC, whitelabeling, group-based permission management across connectors/doc-sets/agents).
- Given "Group-Based Permissions... v4.7+" is called out as EE, this implies at least some connector-adjacent permission tooling was added/expanded in a relatively recent Onyx release (v4.7), reinforcing that this area is actively evolving in 2025-2026.

### Gaps
- Could not find a definitive, itemized public statement that any specific connector (as opposed to the permission-sync feature) is EE-only to even configure/use for basic indexing.
- Could not independently verify the exact current Onyx version number as of Sept 2026 or map "v4.7" to a calendar date.

## Which connectors support Permission Sync / document-level ACL sync?

### Takeaway
Multiple partially-overlapping lists were found across different pages; the most consistently repeated set of permission-sync-capable connectors is: **Confluence, Jira, Google Drive, Gmail, Slack, Salesforce, GitHub, SharePoint**, with **Box and Outlook** also appearing in at least one docs-derived summary. This entire capability is Enterprise-Edition-gated regardless of which connector.

### Cited Findings
- Onyx marketing connectors page: "Auto-sync permissions is available in Onyx Enterprise" and syncs permissions from "Confluence, Jira, GitHub, Google Drive, Gmail, Slack, Salesforce, and SharePoint" — [Onyx Connectors page](https://onyx.app/connectors) (via search-tool summary)
- A docs-overview-derived summary (aggregated from `docs.onyx.app/admins/connectors/overview`) listed permission-sync-supported connectors as: "Confluence, Jira, Google Drive, Gmail, Slack, Salesforce, GitHub, Box, Canvas, SharePoint, Outlook" — this is a broader list than the marketing page and includes Box, Canvas, and Outlook additionally — [Overview - Onyx Documentation](https://docs.onyx.app/admins/connectors/overview) (via WebFetch summary tool, not raw HTML)
- GitHub connector permission sync has a specific operational requirement: "Users must maintain a publicly visible email address on their GitHub profile... Without a public email, the system cannot identify which GitHub permissions apply to which Onyx user." — [GitHub Connector - Onyx Documentation](https://docs.onyx.app/admins/connectors/official/github)
- Three connector access-type configurations exist for any connector generally: **Private** (only creator + explicitly assigned users/groups can see connector's data), **Public** (all Onyx users can see it), and **Auto Sync Permissions** (Onyx maintains an ACL mirrored from the source system, EE-only) — [Overview - Onyx Documentation](https://docs.onyx.app/admins/connectors/overview)
- The `backend/onyx/connectors/interfaces.py` module defines a `CheckpointedConnectorWithPermSync` base class, confirming permission sync is architected as a distinct connector capability/interface in code, separate from plain `LoadConnector`/`PollConnector`/`CheckpointedConnector` — [connectors/README.md](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)
- Backend code confirms a function `source_should_fetch_permissions_during_indexing(source: DocumentSource)` exists in `onyx/access/access.py`, which delegates to an EE-only module (`onyx.external_permissions.sync_params`) to determine per-source whether perm-sync fetching should occur — confirming the EE gate is implemented as a pluggable module boundary rather than hardcoded per-connector logic in the OSS codebase — [access.py](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/access/access.py)
- Connector data model (`connectors/models.py`) includes an `external_access` / doc_metadata field that is "only filled in EE (Enterprise Edition) for connectors with permission sync enabled" — [models.py](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/models.py) (via search-tool summary)

### Inferences
- Because the actual per-source permission-sync implementation logic lives in a separate, presumably closed-source EE module (`onyx.external_permissions.sync_params`), the OSS/CE repository does not itself contain the full authoritative list of which connectors have perm-sync implemented — the public docs pages are the best available proxy, and they disagree slightly (8 vs. 11 connectors) between the marketing page and the docs overview page. Treat the union of both — Confluence, Jira, Google Drive, Gmail, Slack, Salesforce, GitHub, SharePoint, Box, Canvas, Outlook — as the most complete list found, while flagging the marketing-page subset as the "confirmed by two independent pages" tier.

### Gaps
- Could not directly view the underlying EE source code (`onyx.external_permissions.sync_params`) since it is not part of the public OSS repo — could not verify a truly exhaustive/authoritative connector-by-connector perm-sync support matrix.
- Could not confirm whether "Canvas" in the perm-sync list refers to Instructure Canvas (LMS) or another product; the connectors/README-adjacent doc PR ("docs(canvas): document group sync and limits, add UI screenshots") suggests Canvas has distinctive group-sync UI, but full content wasn't fetched.
- Could not verify permission-sync status for many other connectors (e.g., Zendesk, Notion, Linear, HubSpot, Dropbox, Egnyte, Teams, Zoom, etc.) — absence from the found lists is suggestive but not confirmed as "definitely no perm sync," since docs pages for those specific connectors were not individually checked.

## Is there a generic/custom connector framework, and is there a connector SDK?

### Takeaway
Yes — Onyx has a well-defined internal connector framework (not marketed as a separate "SDK" product, but functionally serving that role) documented in `backend/onyx/connectors/README.md`, based on four connector patterns and a set of base interface classes that any new connector must subclass.

### Cited Findings
- Onyx defines four connector patterns: **Load Connector** ("Bulk indexes documents to reflect a point in time" via API/dump files), **Poll Connector** (incrementally refreshes documents within a time range, fetching only recent changes rather than full re-index), **Slim Connector** (lightweight, fetches only document IDs to check existence, used for pruning stale index entries), and **Event-Based Connectors** (listen to source events for real-time updates — described as "currently designed for future implementation," i.e., not yet broadly live) — [connectors/README.md](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)
- New connectors must subclass one or more of `LoadConnector`, `PollConnector`, `CheckpointedConnector`, or `CheckpointedConnectorWithPermSync` from `interfaces.py`; implement `load_credentials()` for auth; and implement `load_from_state()` (full document set) and/or `poll_source(start_time, end_time)` (incremental) depending on pattern — [connectors/README.md](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)
- Connectors that support file attachments should accept an `include_attachments: bool` constructor parameter — defaulting to `False` for new connectors and `True` for retrofitted legacy ones — with attachment enumeration gated on this flag in both the main indexing pass and the slim-doc pass — [connectors/README.md](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)
- To fully add a new connector, contributors must also: add a `DocumentSource` enum entry in `constants.py` and map it in `factory.py` (backend); register it in `SOURCE_METADATA_MAP` and define its form config in `connectorConfigs` (frontend); and create a dedicated documentation page — plus add tests under `backend/tests/daily/connectors` and run lint/format checks before submitting a PR — [connectors/README.md](https://github.com/onyx-dot-app/onyx/blob/main/backend/onyx/connectors/README.md)
- There is also a documented "Create Connector From Model" API reference page, suggesting a programmatic/API-driven way to instantiate connectors, separate from the UI connector picker — [Create Connector From Model - Onyx Documentation](https://docs.onyx.app/developers/api_reference/files_connectors/create_connector_from_model)

### Inferences
- This qualifies as a genuine "build your own connector" framework/contribution path (open, documented, PR-based), functioning like an informal SDK, though Onyx does not appear to brand it publicly as a standalone "Connector SDK" product — it is presented as an internal contribution guide (`connectors/README.md`) rather than a distributed package.
- The explicit note that Event-Based/webhook-style connectors are "currently designed for future implementation" strongly implies that, as of this research date, **no connectors in the current lineup use true real-time webhook push sync** — all current connectors are Load or Poll (scheduled/polling) based, with Slim variants used only for pruning. This directly answers part (a) of the objective at a general/architectural level: sync mechanism across the board is poll/scheduled-pull, not webhook/push, as of Sept 2026.

### Gaps
- Could not find a per-connector breakdown confirming each individual connector's exact pattern (Load vs. Poll vs. Checkpointed vs. CheckpointedWithPermSync) — the general architecture confirms poll-based incremental sync is supported as a category, but this research did not verify connector-by-connector which ones are "Load only" (always full re-index, no incremental) versus "Poll/Checkpointed" (incremental supported). This is a meaningful gap given the objective's requirement to state per-connector incremental-sync support — a follow-up pass fetching individual connector source files (e.g., checking each `connector.py` for `PollConnector`/`CheckpointedConnector` inheritance) would be needed for full per-connector accuracy.
- No dedicated, separately-branded "Onyx Connector SDK" product/package (e.g., a pip-installable SDK) was found; the framework exists as in-repo contribution documentation only.
