# 05 - Agents and automations

Tags: **[V]** read in code (2026-10-12), **[R]** executed during project sessions, **[D]** documented only, **[U]** unknown.

## 0. Maturity vocabulary used below
| Level | Meaning |
|---|---|
| **L1 operational agent** | a loop in which an LLM decides, calls tools, observes results and answers, persisted and reachable from the UI/API |
| **L2 orchestrator calling an LLM** | code that sequences prompts and function calls around an LLM without an open-ended decision loop |
| **L3 chained functions** | deterministic code, no LLM decision |
| **L4 prototype** | exists, narrow, not wired to a user surface |
| **L5 simulation/mock** | produces plausible output without the real dependency |
| **L6 documented only** | described, no implementation |

## 1. The agent runtime (L1) - `AgentOrchestrator` [V]
File `api/services/agent_orchestrator.py` (1,158 lines); class `AgentOrchestrator`; methods `run_agent` (line 172, non-streaming) and `stream_response` (SSE). Used by: the chat stream (`api/services/streaming.py`), message regeneration (`message_actions.py`), the public API (`public_api.py`), telephony (`telephony.py`), agent API keys router.
**Inputs:** `agent_id`, user message, optional `context` (retrieved text) and `citation_chunks`, conversation id, organization/user ids.
**Execution:** create an `AgentRun` row (status machine pending -> running -> completed/failed) and `AgentTrace` rows (`llm_call`, `tool_call`, ... with secrets redacted); resolve the LLM configuration; build the system prompt; run a loop `LLM call -> (tool calls?) -> execute tools (parallel when several) -> append results -> LLM call` up to `AGENT_MAX_TOOL_ITERATIONS=8`; enforce `AGENT_TIMEOUT=60` s and `AGENT_MAX_RETRIES=3`; check credit balance and spend caps before each LLM call, debit after (`_deduct_for_usage`), skip when the organization brings its own key (BYOK); run `validate_guardrails` on the input, on the retrieved context and on the result; on success persist a `Response` with `Citation`s and quality metrics.
**Agent configuration (`agents` table, 38 columns)**: `system_prompt` / `system_prompt_template` (safe `{{variable}}` templating), `model_config_json`, `tools`, memory (`memory_enabled`, window, TTL, max items, retention policy), `guardrails_enabled`, `guardrails_config`, `blocked_topics`, `allowed_domains`, `content_filter_level`, `max_tokens_per_response`, `prompt_injection_detection_enabled`, refusal modes (`citation_required`, `answer_only_from_context`, `idk_threshold`), `human_approval_required`, `knowledge_base_id`/`knowledge_base_config` (retrieval overrides that the Eval Lab also applies), `allowed_users`, `allowed_roles`, `is_public`, `status`.
**Tools available [V: `api/tools/`, `api/services/tools.py`, `tool_wiring.py`]:** `search_knowledge_base` (forces hybrid_reranked), `web_search` (Tavily, needs `TAVILY_API_KEY`), `url_reader`, `sql_tool` (read-only queries scoped to the organization; a tenant-filter bypass was found by red-teaming and fixed), `calculator`, GitHub tools (issues/PRs/code search), calendar and e-mail tools, `human_escalation`, organization-defined **custom tools** (HTTP backed), and external **MCP tools**. Cross-cutting: per-agent and per-user tool permissions (`tool_permissions`), per-tool timeouts and token budgets (`tool_config`), fallback chains (`fallback.py`), result validation (`tool_validation.py`), parallel execution (`parallel_tools.py`).
**Known limits:** the e-mail/calendar/GitHub tools use **server-level accounts** (`GMAIL_*`, `GOOGLE_CALENDAR_*`, `OUTLOOK_*`, `AGENT_SMTP_*`, `GITHUB_API_TOKEN`), i.e. one identity for all organizations (open item of D17); they must stay unset in production until made per-organization. The loop is bounded, not a planner with global memory; a `plan_first` mode (spec 5.1.13) can decompose the task first (`task_planning.py`).

## 2. Memory [V]
* **Short-term** session memory (`agent_memory.py`, `agent_memories`, `agent_sessions`), window/TTL configurable.
* **Cross-session conversation memory** (Part 5.1.12) and **long-term memory items** (`agent_long_term_memory_items`, extraction behind `AGENT_MEMORY_AUTO_EXTRACT`, default false because it adds an LLM call); daily consolidation and cleanup beat tasks. The README also claims Mem0; deletion of derived memory data when a document or organization is erased is flagged as incomplete in earlier audits (see 11_KNOWN_ISSUES).

## 3. Autonomous agents (L1/L2) - `api/services/autonomous_agents.py` (634 lines) [V/D]
Goal-driven agents (Part 23): create a goal, **plan** (LLM decomposition via `task_planning.decompose_task` with cycle/dangling-dependency validation), execute steps in a loop (select tool, call, write result back), tiered memory with semantic recall (embeddings + cosine), agent-to-agent collaboration records (`agent_collaborations`), guardrail checks, per-run cost tracking (`cost_tracking`), human approval for sensitive actions (`human_approvals`), Celery execution (`api/tasks/autonomous_agents.py`). Pages `/dashboard/autonomous-agents[/id]`; 19 routes. Whether a long autonomous run was ever executed end to end against a real LLM in production is **[U]**; unit/integration tests use mocked LLM calls.

## 4. Workflows (L2/L3) - `api/services/workflow_engine.py` [V]
A `workflows` row stores nodes and edges (immutable `workflow_versions`). The engine walks the graph one node at a time (no parallel branches, no join semantics, `MAX_STEPS` bound). Ten block types: `llm_call`, `rag_search`, `web_search`, `http_call` (SSRF-safe), `condition` (the only branch), `code` (restricted expression subset: hardened on 2026-10-11 against format-string dunder reads and memory-growth operators; max code length 5,000 chars, result 1 MB), `human` (persists a pending `WorkflowHumanInput` and pauses; `resume_workflow_run` continues), `email`, `calendar`, `database`. Triggers (`workflow_triggers`): webhook, schedule (beat checks every minute), manual. Per-node execution traces (`workflow_node_executions`). 25 routes; pages `/dashboard/workflows[/id]`.

## 5. The four Bob modes (FACTORY, GUARDIAN, AUTOPSY, CHANGELAB)
Source of definition: `agents.md` (root) sections 2-3; implementation in `api/services/mcp/builtin_tools.py` (4 tools, exposed by `api/routers/mcp_server.py`). They are **a contract for an external engineering agent plus supporting platform services**, not four autonomous in-product agents.

| Mode | Mission (agents.md) | What exists in code [V] | Maturity |
|---|---|---|---|
| **1 FACTORY** | provision tenant RAG agents | MCP tool `create_rag_agent(organization_id, name, model, retrieval_config)` -> validates `retrieval_config` (strategy, top_k, score_threshold, unknown keys rejected) and stores it in `agents.knowledge_base_config`; plus `api/services/agent_factory.py` and routes `agent-factory` (2): a **deterministic, rules-based** blueprint generator (keyword profiles EN+FR; **no LLM call**) -> `validate_blueprint` with the real validators -> real `create_agent` -> optional evaluation on a dataset -> go/hold-back decision; UI `/dashboard/agents/factory` | L3 with a real persistence path (works offline, measurable) |
| **2 GUARDIAN** | watch metrics, alert on degradation | `alert_rules` / `alert_channels` / `alert_history` + `alerting.py` evaluate rules against live data sources (admin monitoring, HTTP counters) and notify by e-mail/webhook; `quality-alerts` (10 routes) and `quality-dashboard` for Recall@5/10, MRR, NDCG, hallucination thresholds per organization; beat tasks `check-alert-rules`, `check-agent-guardrails-hourly`; `regression_thresholds`/`regression_detections` | L2 monitoring; README itself says the "detect -> explain -> propose -> approve -> apply -> roll back" loop is **not automated end to end** |
| **3 AUTOPSY** | explain a failure | MCP tool `get_failure_report(job_id)` (organization-checked after an IDOR fix): joins `evaluation_failures` with questions; categories RETRIEVAL_FAILURE, GENERATION_HALLUCINATION, GENERATION_INCOMPLETE, OTHER; REST `GET /jobs/{id}/failures[/categories]` | L3 (categorisation of recorded failures; hallucination category comes from the computed metric) |
| **4 CHANGELAB** | tune: change, test, evaluate, roll back | MCP tools `update_retrieval_config` (partial merge, validated) and `run_eval_benchmark` (runs the evaluation job **synchronously** in the call, tenant-checked, returns per-metric averages); `rag_evolution_engine.py` (baseline run -> DSPy-proposed candidate **system prompt** -> second run on the same dataset -> metric comparison; **never auto-applies**; single dimension only: it does not search over `top_k`/strategy/chunking); `rag_genome.py` (experiment log); git branch/PR/rollback steps of `agents.md` are a procedure for the external agent, not code | L2 (measured proposals), the closed loop is human/agent-driven |

How they interact in the design: GUARDIAN raises an alert -> AUTOPSY classifies retrieval vs generation failures -> CHANGELAB proposes and benchmarks a change -> FACTORY provisions agents from validated config. In code, the links are *data* links (they share `evaluation_*` tables and `agents.knowledge_base_config`), not an orchestrator that triggers one mode from another. **[V: no code path was found that calls AUTOPSY from GUARDIAN automatically.]**

### Role of IBM Bob 2.0
IBM Bob is an **IDE/CLI coding assistant** (an installation exists on the developer's machine at `...\Programs\IBM Bob\bin`) that the owner used as the "Lead AI Systems Engineer" in a contest entry (IBM Bob 2.0, Sept 2026). `agents.md` is its onboarding contract (modes, guard-rails: never touch existing migrations, never push to `main`, always test, log in `ROADMAP.md [Bob-Auto-Fixes]`), `bob/` holds the demo and evidence (`bob/evidence/json`, `screenshots`), `docs/ibm_bob_2/` holds the contest README and validation reports (including a real-documents run with Recall@5 +0.40). The platform exposes the four MCP tools so an external agent *can* drive the loop. **There is no evidence that Bob runs as a service in production**, and the product does not depend on it at runtime. It is a development-time actor plus a demo of MCP interoperability. The project name changed from the contest's "RAG Evolution Factory" to "RAG SaaS Platform".

## 6. MCP (Model Context Protocol) [V]
* **Server role** (`api/routers/mcp_server.py`, 2 routes): `GET /mcp/v1/tools` lists the 4 built-in tools; `POST /mcp/v1/tools/{name}/call` calls one. Authentication by organization API key header `X-API-Key` with scope `mcp:tools`; each call is organization-scoped and tenant-checked inside the tool.
* **Client role** (`api/services/mcp/client.py`, `discovery.py`, `firewall.py`; routes under `/organizations/{org}/mcp-servers`, 8): register an external MCP server (HTTP/SSE; `stdio` transport disabled unless `MCP_STDIO_ENABLED` and superadmin), sync its tool catalogue (`mcp_tool_cache`), test, call. Every call passes through the **MCP firewall**: OPA policy check (fail-open when OPA is disabled), SSRF protection, and an HMAC-chained audit entry (`AuditAction.MCP_TOOL_CALL`) for allowed, blocked and failed calls. Credentials of MCP servers are encrypted.
* Tools discovered from MCP servers can be added to agents' tool lists.

## 7. A2A and BeeAI [V]
* **A2A (Agent2Agent)** (`api/routers/a2a.py`, `api/services/a2a_integration.py`): an organization exposes **one** agent capability (`run_requirement_agent`) to external A2A clients through an AgentCard and JSON-RPC, authenticated and cost-controlled. Scope is deliberately minimal: no task persistence server features, no push notifications, and **no A2A client** (calling external agents is not built). A post-execution debit risk (credits debited after run) was flagged by the security audit [D].
* **BeeAI Framework** (IBM's open-source agent framework; `api/services/beeai_orchestrator.py`): `run_requirement_agent` (single agent) and `run_multi_agent_team` (coordinator decomposes, one specialist agent per role, coordinator synthesizes). Its only importer in `api/` is the A2A executor (`a2a_integration.py:109`), so it is reachable only through the A2A endpoint [V]; treat it as L2 with narrow exposure. The Factory does not use it (the Factory is rules-based).

## 8. Other automation features
* **Plugins/marketplace** (`plugin_sandbox.py`, `Dockerfile.plugin-sandbox`, 22 routes): third-party plugins run in a sandbox (JS via a real `node` subprocess in tests); hooks (only `on_document_uploaded` is fired from a platform event).
* **Webhooks** (outbound, signed, delivery logs, retry) and **inbound universal webhooks** (Zapier/Make/n8n); chat-platform bots (Slack, Teams, Discord) answer through `handle_public_chat` (`api/services/public_api.py`), which runs `AgentOrchestrator` [V].
* **Fine-tuning** jobs (datasets, jobs, status polling, evaluation, registered models).
* **A/B tests** with significance computed hourly and automatic decision.
* **RAG control plane** (`rag_control_plane.py`): a periodic health check across an organization's A/B tests and experiment history (new behaviour, not a pass-through).
* **Canary rollout**, **cost-aware routing**, **query router**, **flight recorder**, **provenance graph**: standalone services reachable through `rag-control-plane` routes (6).

## 9. Code-reachability check (is anything dead?) [V]
A static scan (`annex/unreferenced_modules.txt`) lists `api/` modules that no other `api/` module imports. Besides entry-point files (routers, tasks, models loaded by name) only **6 library modules** are unreferenced and all six are imported by tests: `api.services.api_versioning`, `api.services.chat_integrations.cards`, `api.services.deepeval_validation`, `api.services.rag_provenance`, `api.tools.calculator`, `api.tools.url_reader`. Conclusion: very little pure dead code at module level; the larger question is *wired but never exercised against real providers* (autonomous agents, A2A, BeeAI, Slack/Teams/Discord, voice), which is a verification gap, not a code-existence gap.

## 10. Safety of automation
Prompt-injection detection is applied to agent input **and** retrieved context in `validate_guardrails` (two-stage, see 06). Code blocks are restricted; HTTP blocks use `ssrf_safe_client`; the SQL tool is read-only and tenant-scoped; human approval gates sensitive actions; spend caps and credits bound LLM cost. `agents.md` itself forbids Bob from using `eval/exec`, `pickle` on untrusted data, SQL f-strings, unauthenticated endpoints, editing past migrations, and pushing to `main`.
