# SQLAlchemy Query Audit (static)

Date : 2026-10-03. Computed by parsing Python AST under `api/`. This is **not** a database query log or proof of tenant isolation. A query call-site count is not a count of SQL statements at runtime: reusable functions can execute repeatedly, and each composed SQLAlchemy statement may contain nested calls.

## Reproducible counting contract

The request specified grep counts; on this Windows host equivalent static counts were collected with Python AST, with this contract:

- `api/*.py` means all Python files recursively under `api/`: 815.
- `files_with_sql_queries`: source files containing one of the patterns `select(`, `db.get(`, `db.execute(`: 234.
- `select()` counts direct SQLAlchemy Name calls named `select`.
- `db.get()`/`db.execute()` count AST calls whose receiver is literally the name `db`; calls via `session`, `conn`, `self.db`, raw cursor, or helper are excluded.
- Explicit tenant filter count is not asserted from regex: the AST cannot reliably associate a predicate written on a later chained expression with the original `select` call. The ledger below defines conservative candidates as a query call whose containing function and call expression contain no literal `organization_id`.

### Reconciliation note (2026-10-03)

An independent AST replay reproduced the broad counts (815 Python files, 234
files with the syntactic patterns, 682 `select()`, 392 literal `db.get()`,
121 literal `db.execute()`, 1,195 combined calls) but classified 656 candidate
call sites without literal `organization_id` in the nearest enclosing
function/call source. A direct count of generated register rows is 660. The
four-row delta is not explained by the preserved command/script for the
original generator (there is no persistent generator), so the 660 register
and 656 independent replay must remain separately reported until reconciled.
Neither count proves missing authorization or an exploitable issue.

## Risk disposition

- No SQL query is declared exploitable from occurrence counts alone.
- Rows on a tenant-owned table without local `organization_id` must be traced through the full caller, authorization dependency, IDs, joins and all child rows. In particular indirect tables require parent ownership binding; user-scoped rows require user checks; control-plane/admin queries need their privileged route guard.
- Task P2C IDOR tests demonstrated two concrete resource-binding gaps, documented and corrected in the Phase 2 report: conversation/message history binding and Stripe PaymentMethod/customer ownership. Those were found by adversarial integration tests, not this SQL heuristic.
- A production-grade audit would add query instrumentation, route-to-service dataflow, reviewed exception allowlists and PostgreSQL RLS tests under a non-bypass role. No DB query or connection was performed here.
